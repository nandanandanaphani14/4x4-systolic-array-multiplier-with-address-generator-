1. Read this first — the one-page summary

An FPGA design is a sea of flip-flops separated by combinational logic. Every clock edge, each flip-flop launches a value that has to arrive at the next flip-flop, settle, and be stable a little before the next edge captures it. Static Timing Analysis (STA) is the tool that checks, for every such path, whether the value gets there in time. It does this exhaustively and without simulating anything — no test vectors, no waveforms, just delay arithmetic over the whole netlist.

Slack is how much time to spare a path has. WNS — Worst Negative Slack — is the slack of the single worst setup path in the whole design. It is one number that answers "does the design run at the requested clock frequency?":

WNS > 0 → every path arrives in time. The design meets timing.
WNS = 0 → the worst path arrives exactly on the deadline. Passing, zero margin.
WNS < 0 → at least one path is too slow. The design fails timing at this clock and may produce wrong results in hardware.

Despite the name, WNS is reported even when it is positive — Vivado prints "Worst Negative Slack" and then shows +0.714 ns. It is really "worst slack"; the word "negative" is historical. A positive WNS is the thing you want, and it is what this project achieved.

2. Why timing analysis exists at all

A flip-flop is not instantaneous. It has three physical requirements, and every one of them is a promise the silicon vendor makes and the designer must not break:

ParameterSymbolWhat it means physically
Clock-to-Q delayTco / Tcq After a clock edge arrives, the flip-flop's output does not change immediately. It takes a small propagation delay before the new value appears on Q.
Setup timeTsu The data at the D input must be stable for this long before the capturing clock edge. Arrive later than that and the flip-flop may not resolve the value correctly.
Hold timeTh The data at D must remain stable for this long after the clock edge. Change too soon and the flip-flop can capture the new value instead of the old one.

Violating setup or hold does not produce a neat error. It produces metastability: the flip-flop output hovers at an undefined level for an unpredictable time before settling to either 0 or 1, effectively at random. Downstream logic sees garbage. The failure is data-dependent, temperature- dependent, and chip-to-chip variable — which is exactly why it must be proven analytically before the bitstream is built, not hunted for in the lab.

The central point a beginner must internalise Simulation checks what your logic computes. Timing analysis checks whether the silicon can compute it fast enough. They are completely independent. A design can pass 3 680 simulation checks with 0 mismatches — as this one does — and still fail in hardware if WNS is negative. Both must pass.

Static, not dynamic

STA is called static because it never applies stimulus. It walks the netlist graph, sums up cell and wire delays along every register-to-register path, and compares the total against the clock period. That makes it exhaustive — it cannot miss a path the way a simulation can miss a corner case — at the price of being pessimistic (it will happily analyse paths that can never be exercised in real operation, which is what timing exceptions in section 18 are for).

3. The anatomy of a timing path

Every path STA analyses has exactly four parts. Learn these four words and the rest follows.

STARTPOINT DATA PATH ENDPOINT (launch FF) (combinational logic) (capture FF) ┌───────────┐ ┌───────────┐ │ Q ├──►[ LUT ]──►[ net ]──►[ LUT ]──►[ carry ]──────► │D │ │ FF_A │ Tlogic + Tnet = data path delay │ FF_B │ │ >CLK │ │ >CLK │ └─────▲─────┘ └─────▲─────┘ │ │ │ launch edge capture edge │ └────────────────┬──────────────────────────────┬──────────────┘ │ CLOCK NETWORK │ │ (BUFG + clock routing) │ source clock delay destination clock delay ───────────────────────────────────────────────────── the difference between these two = CLOCK SKEW
TermDefinition
StartpointWhere the data is launched: a flip-flop clock pin, or an input port.
EndpointWhere the data is captured: a flip-flop D pin, or an output port. Vivado's "number of endpoints" is a count of these capture points — 5 181 of them in our debug build.
Data path delayClock-to-Q of the launch flop, plus every LUT / carry / MUX delay, plus every wire (net) delay in between. In modern FPGAs the net delay is often more than half the total.
Clock path delayHow long the clock edge itself takes to reach each flip-flop, through the global buffer (BUFG) and clock routing.
Clock skewDestination clock delay minus source clock delay. Positive skew (clock arrives at the capture flop later) helps setup and hurts hold. Negative skew does the opposite.
Clock uncertaintyA safety margin the tool subtracts for jitter, PLL/MMCM phase error, and modelling imprecision. You get it for free; it always makes the analysis stricter.
Levels of logicHow many LUTs the signal passes through on the path. A high number is the classic cause of a long path.

4. The setup equation — where WNS comes from

Setup asks: does the data arrive early enough for the next edge? The launch edge and the capture edge are one clock period apart (for a normal single-cycle path).

Data Arrival Time = Tlaunch-clk + Tco + Tlogic + Tnet

Data Required Time = Tcapture-clk + Tperiod − Tsetup − Tuncertainty

Setup Slack = Data Required Time − Data Arrival Time

Expand it and the intuition is plain:

Setup Slack = Tperiod − ( Tco + Tlogic + Tnet + Tsetup ) + Tskew − Tuncertainty

The clock period is your budget. Clock-to-Q, the logic, the wires and the setup requirement are the spending. What is left over is slack. Note what this tells you immediately:

  • Raise the frequency (shrink Tperiod) and slack falls. This is why the same netlist can pass at 100 MHz and fail at 200 MHz — nothing about the logic changed, only the budget.
  • Add logic levels between flops and slack falls. Deep combinational clouds are the number one cause of setup failure.
  • Pipelining fixes setup — inserting a register splits one long path into two short ones, each getting a full period.

The worst setup slack across all paths is WNS. That is the whole definition.

A worked number

Suppose Tperiod = 10.000 ns, Tco = 0.400 ns, logic + net = 8.500 ns, Tsetup = 0.100 ns, skew = +0.050 ns, uncertainty = 0.035 ns:

Slack = 10.000 − (0.400 + 8.500 + 0.100) + 0.050 − 0.035 = +1.015 ns → passes, ~10 % margin

Now ask for 150 MHz instead — Tperiod = 6.667 ns — and with the identical logic:

Slack = 6.667 − 9.000 + 0.050 − 0.035 = −2.318 ns → fails

5. The hold equation — the other half

Hold asks the opposite question: does the data arrive too early? If a path is so short that the new value races through the logic and reaches the capture flop before that same clock edge has finished capturing the old value, the flip-flop captures the wrong data. The launch and capture edges here are the same edge — there is no period term.

Hold Slack = Data Arrival Time − ( Tcapture-clk + Thold )

    = ( Tco + Tlogic + Tnet ) − Thold − Tskew
The single most important asymmetry in all of STA The clock period does not appear in the hold equation. Therefore slowing the clock down cannot fix a hold violation. A design with negative WHS is broken at every frequency, including 1 Hz. Setup failures are a speed problem; hold failures are a structural problem fixed by adding delay (buffers, routing detours) or fixing skew. On FPGAs the placer and router fix hold automatically in almost all cases — a leftover hold violation usually means a genuine design error such as an unconstrained clock crossing.

The worst hold slack across all paths is WHS — Worst Hold Slack. Our debug build reports WHS = +0.045 ns: tight in absolute terms, but positive, with 0 failing endpoints. Small positive hold slack is entirely normal and not a concern — the router targets "just enough" hold margin because over-fixing hold costs setup margin.

6. Slack, WNS, TNS and friends — every term defined

AcronymFull nameMeaning, and how to read it
WNSWorst Negative Slack The smallest setup slack of any path in the design. One number. Positive → all setup paths pass. This is the headline timing metric and the answer to "did it close?".
TNSTotal Negative Slack The sum of the slacks of all failing setup endpoints (passing endpoints contribute 0). TNS = 0 means nothing fails. TNS tells you how much of the design is failing, where WNS tells you only how badly the worst one fails. WNS = −0.05 ns with TNS = −0.05 ns is one lazy path; WNS = −0.05 ns with TNS = −900 ns is a design-wide problem.
WHSWorst Hold Slack The smallest hold slack of any path. Must be positive. Cannot be fixed by lowering frequency.
THSTotal Hold Slack Sum over all failing hold endpoints. Should be 0.000.
WPWSWorst Pulse Width Slack Checks that the clock pulse itself is legal — that its high time and low time are longer than the minimum the flip-flop, BRAM or DSP requires, and that the clock period is not shorter than the cell's own minimum period. This catches broken clock division, badly configured MMCMs, and clocks that are too fast for a hard block.
TPWSTotal Pulse Width Negative SlackSum over failing pulse-width checks. Should be 0.000.
Failing endpoints— How many capture points have negative slack. 0 is the only acceptable value for sign-off.
Total endpoints— How many capture points were analysed at all. Useful as a sanity check: if this number is suspiciously small, large parts of your design are unconstrained and therefore not being checked.
FmaxMaximum frequency Not printed directly. Derive it: Fmax = 1 / (Tperiod − WNS). It is an estimate, valid near the constrained frequency only.

7. Endpoints, path groups and what "0 failing" means

Vivado groups paths so you can see which kind of path is the problem. In the timing summary GUI these appear as a tree:

GroupWhat lives there
Intra-Clock PathsLaunch and capture flops on the same clock. In this project, essentially the entire design: everything runs on sys_clk.
Inter-Clock PathsLaunch and capture on different clocks. Real CDC lives here. In this project, only the JTAG/debug-hub boundary — and Vivado's debug IP constrains that itself.
Other Path GroupsSpecial groups such as **async_default** — paths through asynchronous set/reset pins.
User Ignored PathsPaths you removed from analysis with set_false_path / set_clock_groups. Always read this list. A design "passes" trivially if you have falsely ignored the failing paths.
Unconstrained PathsPaths with no clock definition reaching them. These are not analysed at all. They are invisible in WNS and are the classic way a broken design shows a beautiful timing summary.
Check TimingA separate audit (our build shows 8 377 entries) listing structural issues: no_clock, constant_clock, unconstrained_internal_endpoints, no_input_delay, no_output_delay, etc. High counts here are normal for a PL-only design with no external I/O interface, but they must be understood, not ignored.
"0 failing endpoints" is only meaningful together with the endpoint count 0 failing out of 5 181 analysed is a real pass. 0 failing out of 12 analysed means you forgot to write a create_clock and the tool checked almost nothing. Always read the two numbers as a pair, and always run check_timing and report_clocks before believing a summary.

8. Why simulation passing is not timing passing

This project has a very strong functional baseline: 11 of 11 testbenches, 3 680 checks, 0 mismatches in the QuestaSim re-verification regression. It is worth being precise about what that does and does not prove.

QuestionAnswered by simulation (RTL)Answered by STA
Is the maths right — does C = A × W?Yes. 3 680 checks say so.No. STA has no idea what the design computes.
Is the FSM phase sequence right (WLOAD 4, COMPUTE N, DRAIN 8, DONE 1)?Yes.No.
Will the silicon actually hit 100 MHz?No. RTL simulation is zero-delay; every gate is instantaneous.Yes. That is exactly what WNS answers.
Is there a setup violation on a 32-bit adder in a PE?No.Yes.
Is the clock pin constrained to the right package pin?No.Partly — check_timing flags the missing constraint; the XDC does the placement.

The two are orthogonal and both are mandatory. A design that computes the right answer at a clock frequency it cannot sustain will produce wrong answers in hardware while simulating perfectly, which is one of the most confusing failure modes a beginner can meet. That is why the hardware bring-up in implementation_method.pdf re-runs the same golden T5 vector on the board: it proves the functional result and the timing result at once.

9. This design's clock and constraint

The entire accelerator is a single-clock, fully synchronous design. There is exactly one clock, and it is constrained in one line:

## ---- 100 MHz on-board PL clock (Bank 13, GCLK) ----------------------
set_property -dict {PACKAGE_PIN Y9 IOSTANDARD LVCMOS33} [get_ports clk]
create_clock -name sys_clk -period 10.000 [get_ports clk]
PropertyValueConsequence for timing
Clock sourceZedBoard 100 MHz PL oscillator, package pin Y9A real board oscillator, not a PS-derived FCLK. The PL runs even with no PS software loaded.
Period constraint10.000 nsThe budget every path is measured against. This is Tperiod in section 4.
Clock namesys_clkNaming the clock makes every later constraint and report readable.
Duty cycle50 % (default)High time = low time = 5.000 ns. This is what the pulse-width check measures against.
Number of clock domains1 (plus the debug hub's JTAG domain, self-constrained by the IP)No CDC to constrain, no set_clock_groups, no asynchronous FIFO. A large class of timing problems simply does not exist here.

Why "constrain the source, not the buffer output" create_clock is applied to [get_ports clk] — the package pin — not to the output of the BUFG. Constraining the buffer output makes the tool ignore the buffer's own delay and produces optimistic, wrong numbers. Constrain where the clock physically enters the chip and let the tool propagate it forward.

10. Where the timing paths in this design actually are

11. The critical path — the PE multiply-accumulate

The longest combinational cloud in this design is inside processing_element (MAC.sv). This is the only module in the whole accelerator that contains arithmetic, and there are sixteen copies of it:

// Combinational arithmetic
assign product_ext = 32'(weight_q * a_in);      // signed 8 × signed 8, sign-extended to 32
assign adder_out   = psum_in + product_ext;     // 32-bit signed add

always_ff @(posedge clk) begin
    ...
    psum_q <= valid_in ? adder_out : psum_in;   // accumulate OR bypass
end

assign psum_out = wload ? 32'(weight_q) : psum_q;   // COMBINATIONAL output mux

Trace the worst path from one row of the array to the next:

PE(r,c) PE(r+1,c) ┌────────────────────────┐ ┌────────────────────────┐ │ psum_q ──┐ │ │ │ │ ├─► [ mux ] ──┼── psum_out ─── net ──────┼──► psum_in │ │ weight_q─┘ (wload) │ │ │ │ └────────────────────────┘ │ ▼ │ │ [ 32-bit ADDER ] ◄── product_ext a_q (west PE) ─── net ──► a_in ──► [ 8×8 SIGNED MULTIPLIER ] ◄── weight_q (mapped to LUT fabric — 0 DSPs used) │ │ │ │ ▼ │ │ [ mux (valid_in) ] │ │ │ │ │ ▼ psum_q ◄──── capture FF └────────────────────────┘ Path = FF(clk-to-Q) → output mux → routing → 32-bit carry chain → valid mux → FF(setup) In parallel: FF(a_q) → routing → 8×8 signed multiply (LUT array) → into the same adder

Why 0 DSPs is the interesting part

The measured utilisation report says DSPs: 0 of 220 (0.00 %). Vivado mapped all sixteen 8×8 signed multipliers into general LUT fabric, not into DSP48E1 slices. The consequences:

ConsequenceDetail
Slower per multiplyA fabric multiplier is a tree of LUTs and carry logic. A DSP48E1 has a hardened multiplier and is faster and far more compact.
Explains the LUT count1 564 LUTs for a design this small is dominated by sixteen fabric multipliers plus sixteen 32-bit adders.
It is still fast enoughAn 8×8 multiply is small. The synthesiser judged the fabric implementation would meet 10 ns, and the measurement (+1.279 ns / +0.714 ns) confirms it.
It is the first lever if you ever raise the clockForcing DSP inference — (* use_dsp = "yes" *) on the module, or synth_design -max_dsp tuning — would shorten this path substantially and free ~1 000 LUTs. It is the single highest-value change if you ever target 200 MHz.
Why the adder, not the multiplier, is usually the deeper half An 8×8 product needs only a shallow partial-product tree. The 32-bit addition that follows it propagates a carry across 32 bits — on 7-series that maps to the dedicated CARRY4 chain, which is fast but is a genuine serial dependency. Add the two output muxes and you have the design's longest cloud. This is also why the accumulator width matters: widening psum to 48 bits would directly cost setup slack.

12.5 Bus skew — the CDC check you did not write

A bus-skew constraint is different from setup and hold. It does not ask "did each bit arrive in time?" but "did all the bits of this bus arrive close enough together?" — which is the question that matters for a gray-coded pointer crossing between clock domains, where two bits changing on different clock edges corrupts the pointer even though every individual path meets timing.

You did not write these constraints; Xilinx's debug IP supplied them for its own asynchronous FIFOs. Vivado checked them anyway, and they pass with enormous room:

  • 7.1 % is a working margin, not a luxurious one. It is entirely adequate for a design that is programmed, run and observed on a bench at a fixed 100 MHz. It is not the kind of margin that would survive being asked for 150 MHz.
  • The debug cores cost ~0.565 ns of setup slack (1.279 → 0.714). That is the price of observability, and it is worth stating explicitly: instrumenting a design is not free in timing, because the probes contend for the same routing resources as the logic they observe.

Do not treat Fmax as a promise Fmax derived from WNS is a linear extrapolation from one operating point. Re-constraining the design at 114 MHz will not reliably give WNS = 0 — the tools optimise to the constraint, so a tighter constraint changes placement, routing and even logic mapping. The only way to know the real Fmax is to re-run implementation at the new period and read the new WNS.

14. Cycles per matrix multiplication — latency and throughput

WNS tells you how fast one clock cycle may be. It says nothing about how many cycles the job takes. Both are needed before you can state how long a matrix multiplication actually costs, and the second number comes not from Vivado but from the RTL — specifically from the phase counters in controller.sv. This section derives it.

14.1 The six phases and their exact durations

The controller is a five-state machine with fixed, data-independent phase lengths. There is no back-pressure, no handshake and no stall condition anywhere in the design, so the cycle count is not an average or a typical case — it is exact, every time:

PhaseDuration (parameter)4×4 valueWhat is happening
IDLEreference point— start is sampled and num_vectors latched; the state moves to WLOAD on that same edge. Latency is measured from this edge, so this cycle is the zero point rather than a term in the total. It is counted in the issue interval.
WLOADROWS4 The four weight rows are shifted into the array, bottom row first, one row per cycle. Skipped entirely when the array already holds the right weights — see §14.4.
COMPUTEnum_vectors = N4 One activation vector issued per clock. This is the only phase that does useful arithmetic, and the array is fully busy for all of it.
DRAINSTORE_LATENCY = 1 + ROWS + COLS − 2 + 18 The last activation vector issued is still in flight through the skew buffer, the array, the de-skew buffer and the output write port. The FSM waits exactly as long as that pipeline is deep.
DONE11 done pulses high for one cycle, then the machine returns to IDLE.

The IDLE cycle is the reference point, not a term in the sum: latency is measured from the edge that samples start, so the phases that follow it are what get counted.

Weights loaded = ROWS + N + STORE_LATENCY + 1(DONE) = 4 + N + 8 + 1 = N + 13
Weights reused =         N + STORE_LATENCY + 1(DONE) =      N + 8 + 1 = N + 9

For one complete 4×4 × 4×4 matrix multiplication, N = 4:
4 + 13 = 17 clock cycles = 170 ns at 100 MHz
4 + 9  = 13 clock cycles = 130 ns when the weight matrix has not changed

Counting the IDLE cycle as well gives N + 14 = 18 (or 14) — the issue interval, i.e. how often a new start can be accepted, not the latency.

Weight reuse is automatic — you get the 13-cycle path for free accelerator_system_top keeps a one-bit weights_dirty flag. It is set by any host write to weight_mem that actually reaches the SRAM, cleared on the final WLOAD cycle, and set by reset. It drives controller.load_weights, so a job whose weight matrix has not changed skips WLOAD entirely and finishes in N + 9. Nothing in the host protocol changes and the module's port list is unchanged — fpga_top, vio_debug_top and accel_axi all benefit without modification. Verified in tb_accelerator_system_top T7/T8: a reuse job measures 13 cycles with WLOAD never entered and results bit-identical to a full-load job, and rewriting one weight row puts the next job back on the 17-cycle path.

The bring-up consequence On the board, a 4×4 multiplication finishes in 230 nanoseconds — roughly ten thousand times faster than a human can click a VIO button. This is precisely why done has to be made sticky in vio_debug_top and why the ILA is triggered on start rather than polled: the entire computation is over long before any JTAG transaction can observe it in flight. The 17-cycle figure is therefore not just a performance number, it is the reason the debug architecture looks the way it does.

15. Why this design closes timing so comfortably

The positive WNS is not luck. It is a consequence of specific architectural choices, and being able to name them is far more valuable than quoting the number:

Design propertyWhy it helps timing
Systolic architecture: short local links only The defining property of a systolic array. Every PE talks only to its immediate north/west neighbours through a register. There are no long global buses, no broadcast nets, and no combinational path that crosses the array. This is the single biggest reason the design is fast, and it is why systolic arrays are used for high-frequency accelerators in the first place.
Every PE output is registered a_q, valid_q, psum_q and weight_q are all flip-flops. Combinational logic never spans two PEs — except the wload shift mux, which is active only during the 4-cycle weight load when nothing else is happening.
Deeply pipelined by construction The 8-cycle store latency is not overhead invented for timing — it falls out of the dataflow (3 down the column, +c east, +(3−c) de-skew, +1 memory, +1 strobe). A design whose correctness model is already pipeline-shaped tends to close timing without extra effort.
Narrow datapath: int8 in, int32 accumulate 8×8 multipliers are small. A 32-bit accumulator carry chain is one CARRY4 column group. Had this been 16×16 or float, the critical path would be several times longer.
Tiny control logic A 5-state FSM with fixed phase durations, and an AGU built from counters and a shift register. No wide comparators, no priority encoders, no arbitration in the datapath.
No back-pressure, no handshakes There is no ready/valid negotiation anywhere. Handshake logic creates combinational paths that run backwards through a pipeline and is a common source of critical paths. Fixed latency removes the whole category.
Very low utilisation (2.9 % LUT, 0.7 % FF) The placer has the entire device to spread into and the router has abundant free channels. Net delay — often more than half the path — stays small. Timing gets dramatically harder above roughly 70–80 % utilisation.
Single clock domain, synchronous reset No CDC, no clock groups, no recovery/removal analysis on asynchronous resets, no MMCM phase relationships to get wrong.
Modest target frequency 100 MHz on a 7-series device is a relaxed target. The board oscillator sets it; the design does not need more.

18. What to do when WNS is negative — ordered checklist

Work down this list. It is deliberately ordered cheapest-and-most-likely first.

20. Clock domain crossing and this design

CDC is where most real timing disasters live, so it is worth stating precisely why this project is mostly exempt — and where the one crossing is.

  • The accelerator itself has exactly one clock. Every flip-flop in accelerator_system_top is on sys_clk. There is no crossing to synchronise, so no two-flop synchronisers, no gray-coded pointers, no async FIFOs.
  • The reset is synchronous and glitch-free by construction. A 16-bit counter holds rst_n low for 65 536 clocks (≈ 655 µs) after configuration, then releases it synchronously. Synchronous release means no recovery/removal timing problem.
  • The one real crossing is JTAG ↔ fabric, inside the debug hub. You do not design or constrain it — Xilinx's debug IP owns both sides. Your one obligation is to tell it the truth about the fabric clock: 
    set_property C_CLK_INPUT_FREQ_HZ  100000000 [get_debug_cores dbg_hub]
set_property C_ENABLE_CLK_DIVIDER false     [get_debug_cores dbg_hub]
    Getting this wrong is the number-one cause of "The debug hub core was not detected".
  • The VIO's level-to-pulse conversion is not a CDC problem, it is a rate problem. A VIO probe_out is already synchronous to clk; the issue is that a human holds it high for milliseconds while the accelerator wants a one-clock pulse. That is solved in logic by the oneshot module, not by a synchroniser. See implementation_method.pdf §4.

23. WNS for preparation — interview / viva question bank

These are the questions actually asked about this topic, with answers at the level expected. The short answer is what you say first; the follow-up is what a good candidate adds.

Q1. What is WNS?
Worst Negative Slack — the smallest setup slack among all timing paths in the design. Slack is required time minus arrival time, so WNS tells you how much margin the single worst path has. Positive WNS means every setup path meets timing at the constrained frequency; negative WNS means at least one path is too slow and the design does not close. The word "negative" in the name is historical — the value is reported whether it is positive or negative.
Q2. What WNS did your design achieve, and at what frequency?
On xc7z020clg484-1 constrained at 100 MHz (create_clock -period 10.000): the accelerator alone synthesises to WNS +1.279 ns, and the full ZedBoard debug build with the VIO, ILA and debug hub reports WNS +0.714 ns, TNS 0.000, 0 failing endpoints of 5 181, with WHS +0.045 ns and WPWS +3.750 ns, and Vivado's "All user specified timing constraints are met." So roughly 7 % margin on the 10 ns period in the build that actually runs on the board, which corresponds to an estimated Fmax of about 108 MHz.
Q3. What is the difference between WNS and TNS?
WNS is the worst single path's slack; TNS is the sum of the negative slacks of all failing endpoints. WNS tells you how bad the worst offender is; TNS tells you how widespread the failure is. WNS = −0.1 ns with TNS = −0.1 ns is one path to fix; WNS = −0.1 ns with TNS = −500 ns means thousands of endpoints are failing and the problem is systemic — usually over-constraining or congestion, not one bad path.
Q4. Write the setup slack equation.
Setup slack = Tperiod − (Tco + Tlogic + Tnet + Tsetup) + Tskew − Tuncertainty, or equivalently required time minus arrival time, where arrival = launch clock path + Tco + data path, and required = capture clock path + period − Tsetup − uncertainty.
Q5. Can you fix a hold violation by reducing the clock frequency?
No. The clock period does not appear in the hold equation — hold compares the launch and capture at the same edge. A hold violation exists at every frequency including DC. You fix it by adding delay on the short path, by fixing clock skew, or by fixing the structural cause (often a missing synchroniser on a clock crossing). Setup, by contrast, is fixed by slowing the clock, because the period is the budget.
Q6. What is the critical path of your design?
The multiply-accumulate inside processing_element: from a PE's psum_q register, through the combinational wload output mux, across the routing to the PE below, into the 32-bit signed adder whose other operand is the 8×8 signed product weight_q * a_in, through the valid_in accumulate/bypass mux, into the next psum_q register. Utilisation shows 0 DSPs used, so all sixteen multipliers were mapped into LUT fabric — which is why LUT count is 1 564 and why forcing DSP48E1 inference would be my first move if I had to raise the clock.
Q7. Why does your design have positive slack — what did you do to get it?
Mostly architecture rather than tuning. A systolic array has only short, local, register-to-register links — every PE talks solely to its north and west neighbours through a flip-flop, so no combinational path spans the array. The datapath is narrow (int8 × int8 into int32). The control is a 5-state FSM with fixed phase lengths and there is no ready/valid back-pressure logic, so no combinational path runs backwards through the pipeline. Utilisation is 2.9 % LUT / 0.7 % FF, so routing is uncongested. And 100 MHz is a relaxed target for a 7-series part.
Q8. Your WNS dropped from +1.279 ns to +0.714 ns. Why?
Two separate reasons. First, +1.279 ns was post-synthesis and out-of-context with no debug logic; post-synthesis estimates on 7-series are optimistic because routing is not yet real. Second, the board build adds the VIO, the ILA and the auto-inserted debug hub — thousands of extra flip-flops and, more importantly, competition for routing resources near the logic being probed. The endpoint count rising from 1 305 to 5 181 is the visible evidence. Both builds still pass with zero failing endpoints.
Q9. Your WHS is only +0.045 ns. Is that a problem?
No. Hold slack is pass/fail, not a margin you bank. The router deliberately inserts only just enough delay to fix hold, because every hold buffer it adds eats setup margin. +0.045 ns with 0 failing endpoints and THS 0.000 is a normal, healthy post-route result. What would worry me is a negative WHS, because that indicates a structural problem the router could not fix.
Q10. What is WPWS, and why is yours exactly +3.750 ns in both builds?
Worst Pulse Width Slack checks that the clock waveform itself is legal — minimum high time, minimum low time, and minimum period for each cell. With a 10 ns clock at 50 % duty the high pulse is 5.000 ns, and the 7-series minimum high pulse for a BUFG-driven flip-flop is 1.250 ns, so the slack is 5.000 − 1.250 = 3.750 ns. It is a property of the clock, not of the logic, which is exactly why adding the entire debug infrastructure did not change it at all.
Q11. If your timing summary showed WNS positive but you still got wrong results on the board, what would you check?
First, whether the analysis was complete: run check_timing and report_clocks and look at the unconstrained-path count — a beautiful WNS over 12 analysed endpoints means nothing was checked. Second, whether I hid the failure with a set_false_path or an incomplete set_multicycle_path — I would read the "User Ignored Paths" group. Third, whether the problem is not timing at all: for this design the usual suspects are the host protocol rather than the silicon — writing weight rows in reverse order, issuing start while busy is high so it is ignored, or driving a VIO level instead of a one-clock pulse.
Q12. Is post-synthesis timing enough to sign off?
No. Post-synthesis delays are estimates with no real routing. Sign-off is post-route — open_run impl_1 then report_timing_summary. That is the Design Timing Summary quoted for the board build here.
Q13. How would you take this design to 200 MHz?
In order: (1) force the multipliers into DSP48E1 hard blocks with (* use_dsp = "yes" *) — the biggest single win, since the MAC is the critical path and 0 DSPs are currently used; (2) pipeline the multiply and the add into separate stages, then update RESULT_LATENCY, STORE_LATENCY, the AGU write-pipe depth and the controller's DRAIN length consistently, because this design has fixed latency and no back-pressure — an inconsistent change writes results to the wrong addresses; (3) shrink or remove the debug cores; (4) use stronger implementation directives and, if congestion appears, floorplan the array. Then re-run implementation at the new period and read the new WNS, rather than trusting the Fmax extrapolation.
Q14. What does "0 failing endpoints of 5 181" mean?
5 181 capture points — flip-flop D pins and output ports — were analysed, and none of them has negative slack. The second number matters as much as the first: it confirms the analysis actually covered the design. If it had said "0 failing endpoints of 12", I would go looking for a missing create_clock.
Q15. What is clock uncertainty and can you get rid of it?
A margin the tool subtracts from the required time to account for clock jitter, MMCM/PLL phase error and modelling imprecision. You cannot remove it and should not want to — it is what keeps the analysis from being optimistic. You can tighten it deliberately with set_clock_uncertainty to build in extra guard band, which makes timing harder to close on purpose.
Q16. Simulation passed all 3 680 checks. Doesn't that prove the hardware works?
It proves the logic is right, not that the silicon can run it at 100 MHz. RTL simulation is zero-delay — every gate is instantaneous — so it can never detect a setup violation. Functional correctness and timing closure are independent, and both are required. That is why the hardware bring-up replays the same golden T5 vector on the board through the VIO: a match there proves the function and the timing together.
Q17. How many clock cycles does one matrix multiplication take?
17 cycles for a 4×4 × 4×4 multiplication — 170 ns at 100 MHz — and 13 cycles (130 ns) when the weight matrix has not changed since the last job. Measured from the edge that samples start, it breaks down as ROWS = 4 cycles of WLOAD to shift the weight matrix in, N = 4 cycles of COMPUTE (one activation vector per clock), STORE_LATENCY = 8 cycles of DRAIN while the last result is still in flight, and 1 DONE cycle: 4+4+8+1 = 17. In general it is N + 13, or N + 9 when WLOAD is skipped, and because there is no back-pressure anywhere in the design those figures are exact rather than typical. Counting the IDLE cycle too gives the issue interval for back-to-back jobs, 18 or 14. There is deliberately no FLUSH phase — see Q22.
Q18. What throughput is that, and why is it so far below the peak?
A 4×4 × 4×4 multiply is 64 MACs, so 64 MACs in 17 cycles is 3.76 MAC/cycle = 0.38 GMAC/s at 100 MHz. The peak is 16 MACs/cycle = 1.6 GMAC/s = 3.2 GOP/s, because all sixteen PEs are busy every cycle of the COMPUTE phase. The gap is entirely the 13 fixed overhead cycles: efficiency is N/(N+13), which is 23.5 % at N = 4 but 95 % at N = 255. That is the weight-stationary trade-off — the weights are loaded once and amortised over however many activation vectors you stream against them, so a single isolated 4×4 multiply is the architecture's worst case.
Q19. How would you make it faster without raising the clock?
Both of the obvious levers are already implemented. Weight reuse: 4 of the 13 fixed cycles exist only to install the weight matrix, and the weights are stationary, so a job whose weight matrix has not changed skips WLOAD and runs in 13 cycles instead of 17 — automatically, via the weights_dirty flag in accelerator_system_top. Removing FLUSH: an earlier revision inserted 6 more cycles between WLOAD and COMPUTE to let weight residue drain out of the psum registers; that was margin rather than function and has been deleted (Q22). Together those took a 4×4 job from 17 cycles to 17, or 13 on a repeat. What remains: increase N so the fixed cost amortises — no RTL change at all — or raise the clock, which costs timing margin (Q13).
Q20. What does the design consume, and where does the power go?
0.145 W total on-chip, of which 0.104 W is device static leakage and only 0.042 W is dynamic; junction temperature 26.7 °C against a maximum ambient of 83.3 °C. The interesting part is the hierarchy breakdown: the ILA takes 0.019 W, the VIO 0.007 W and the debug hub 0.003 W — 69 % of all dynamic power is instrumentation — while the accelerator itself takes 0.012 W and the entire 4×4 PE array takes 0.003 W. At 170 ns per multiply that is about 8 pJ per MAC for the arithmetic and 385 pJ per MAC once static leakage and debug logic are counted. Worth caveating: it is a vector-less estimate at medium confidence, because under 25 % of internal nodes had specified toggle rates.
Q21. You said the timing summary is clean. What else did you check before believing it?
Four things beyond the WNS line. report_methodology: 16 warnings but zero TIMING-* violations, which is the family that catches missing clocks and unconstrained paths — that is independent evidence the analysis was complete. report_bus_skew: the four gray-pointer CDC buses in the debug hub pass with 0.747 ns of skew against a 10 ns requirement. report_clock_utilization: both clocks are on real BUFGs and the clock pin is on an MRCC site, so skew is genuinely small rather than accidentally optimistic. report_drc: 0 errors, 0 critical warnings. The one finding that is actually ours is SYNTH-6 — a_mem's output register was not merged into the BRAM — which costs nothing today but would become the critical path if the MAC were ever moved into DSP48E1 slices.
Q22. Your FSM has no FLUSH phase. Didn't the weight load leave residue in the psum registers?
It does, and it does not matter. Two independent reasons. Accumulation is never at risk: in MAC.sv the accumulator is psum_q <= valid_in ? (psum_in + product) : psum_in — a PE's own psum_q is only ever an output of the adder, never an input, so the chain is fed entirely from the row above and stale content is overwritten rather than accumulated into. The residue can never reach memory: it drains out of the bottom of the array at one row per cycle and clears the de-skewed result bus on cycle 12, while the first out_we — the AGU's write-strobe pipe, keyed off compute_phase and STORE_LATENCY deep — does not fire until cycle 13. The two trains move at the same rate and cannot converge. Removing FLUSH cut 6 cycles from every job with no functional change, confirmed by 187 checks at system level including two full signed 4×4 × 4×4 multiplications. The honest caveat: the margin is now zero, so anyone adding a pipeline stage in the skew → array → de-skew → pack path must re-derive that table.

CDCClock Domain Crossing. Not present in this accelerator; only the JTAG/debug-hub boundary, owned by Xilinx IP.
MetastabilityThe undefined-output condition that a setup/hold violation causes.
Bus skewHow far apart in time the bits of one bus arrive. Checked by report_bus_skew; the check that matters for gray-coded CDC pointers.
Control setThe {clock, clock-enable, set/reset} triple. All 8 flops in a 7-series slice must share one; too many distinct sets means bad packing.
MRCC / SRCCMulti- / Single-Region Clock Capable I/O pin. A clock must enter on one to reach a BUFG cleanly. clk is on Y9 = IO_L12P_T1_MRCC_13.
Static vs dynamic powerLeakage (a property of the die) vs switching (a property of your design). Here 0.104 W vs 0.042 W.
Job latencyCycles from start to done. Here N + 13 (= 17 for a 4×4), or N + 9 (= 13) when WLOAD is skipped.
Issue intervalCycles before the next start is accepted. Here N + 14 = 18, or N + 10 = 14.
Array efficiencyFraction of cycles the PEs do useful work: N/(N+13). 23.5 % at N = 4, 95 % at N = 255.
weights_dirtyInternal flag in accelerator_system_top that skips WLOAD when the array already holds the right weight matrix.
GMAC/sBillion multiply-accumulates per second. Peak here = 16 PEs × 100 MHz = 1.6 GMAC/s (3.2 GOP/s).
