1. What this method gives you

The accelerator finishes a four-vector job in 17 clock cycles = 170 ns at 100 MHz. That is far too fast for a human to watch on LEDs, and eight switches cannot hold a 4×4 int8 matrix. Method 1 (switches + LEDs) works around this with a byte-at-a-time console FSM. Method 2 removes the board from the loop entirely: the JTAG programming cable carries both the stimulus and the observation.

Read this section before building anything. Four properties of accelerator_system_top completely determine the shape of the debug harness.

3.2 Host protocol

1.  hold rst_n low, then release
2.  while (!busy):  write weight rows   via host_w_*   (4 words)
                    write activations   via host_a_*   (num_vectors words)
3.  pulse start, with num_vectors / act_base / out_base valid
4.  wait for the done pulse             (job length = num_vectors + 13 clocks)
5.  while (!busy):  read results        via host_o_addr -> o_rdata

3.3 The four properties that shape the harness

#PropertyConsequence for a VIO-driven design
1Every command is a single-cycle pulse. start, host_w_we, host_a_we. A VIO probe_out is a level — it stays where you left it for milliseconds until you click again. Holding start high would relaunch the 17-cycle job roughly 4 million times per second; the ILA would retrigger continuously and never let you inspect a single run. The harness edge-detects every command bit (oneshot module).
2done is one cycle wide (10 ns). VIO refreshes at human rate and will never observe it. The harness latches it into done_sticky, cleared automatically by the next start pulse. A 16-bit done_count is also provided so you can prove exactly one job ran per click.
3Host writes are masked while busy==1. Port arbitration at L3 forces a_we_mux = w_we_mux = 0 during a job. Harmless but silent: a write clicked mid-job simply vanishes. Always confirm busy==0 on the dashboard before loading. Because JTAG round-trips take milliseconds and a job takes 170 ns, this is essentially never a problem in practice.
4Fixed latency, no back-pressure. No ready/valid handshake exists anywhere in the design. Nothing will stall to wait for you. Every timing number in section 13 is a hard constant, which is exactly what makes the ILA capture checkable against the specification.

3.4 Data layout — get a lane wrong and the matrix silently transposes

weight_mem[r]   [31:24][23:16][15:8][7:0]  =  W[r][3] W[r][2] W[r][1] W[r][0]   (lane c = column c)
a_mem[i]        [31:24][23:16][15:8][7:0]  =  A[i][3] A[i][2] A[i][1] A[i][0]   (lane r = row r)
output_mem[i]   [127:96][95:64][63:32][31:0] = C[i][3] C[i][2] C[i][1] C[i][0]  (lane c, int32)
The bottom-first rule is not yours to apply The design's rule 1 says "weight rows load bottom-first". That is the AGU's job — during WLOAD it counts w_addr down 3, 2, 1, 0. As the host you write weight_mem[r] = W row r in natural order 0, 1, 2, 3. Pre-reversing them here is a classic and silent error: the result is a plausible-looking but wrong matrix.

4. The debug harness vio_debug_top.sv

The harness is deliberately thin. It adds exactly four things around the unmodified accelerator:

  1. A power-on reset. A 16-bit counter holds rst_n low for 65 536 clocks (≈655 µs) after configuration. The declaration initializer (logic [15:0] por = '0;) is a synthesizable power-up value on Xilinx 7-series — flip-flops configure to a known state at bitstream load, so no external reset pin is required.
  2. Three oneshot instances. Rising-edge detectors on vio_start_lvl, vio_w_we_lvl, vio_a_we_lvl. Property 1 above.
  3. Sticky done + a job counter. Property 2 above.
  4. A flattening assign. result[0:3] is an unpacked array and cannot be wired to a probe port; result_flat concatenates it into one 128-bit vector.
// the load-bearing 10 lines of the harness

// level -> single-cycle pulse                       (property 1)
oneshot u_os_start (.clk(clk), .rst_n(rst_n), .lvl(vio_start_lvl), .pulse(start_p));
oneshot u_os_wwe   (.clk(clk), .rst_n(rst_n), .lvl(vio_w_we_lvl),  .pulse(w_we_p));
oneshot u_os_awe   (.clk(clk), .rst_n(rst_n), .lvl(vio_a_we_lvl),  .pulse(a_we_p));

// catch the 10 ns done pulse                        (property 2)
if      (start_p) done_sticky <= 1'b0;   // arm for the new job
else if (done)    done_sticky <= 1'b1;   // latch
if (done) done_count <= done_count + 1'b1;

// unpacked array -> probeable vector
assign result_flat = {result[3], result[2], result[1], result[0]};
Why oneshot is not optional Without it the design still computes correctly — the job is idempotent, so re-running it gives the same answer. What breaks is observability: busy never reads 0 on the dashboard, done_sticky is cleared as fast as it is set, and the ILA arms and fires continuously so you can never freeze a single 17-cycle window. It is the difference between a working demo and an unreadable one.

Why is the activation address 8 bits but the weight address only 2? This looks like an inconsistency the first time you see the dashboard — both matrices are 4×4, and for this demo you write exactly four words to each. It is not a mistake, and it is not something you should "fix". The two address buses are sized for the memories behind them, and those memories differ in depth by 64×:
ProbeWidthMemoryGeometryWhy that depth
vio_w_addr2weight_mem4 × 32Holds one whole matrix, once. The array has ROWS = 4 rows; each 32-bit word packs the four int8 weights of one row. Four rows ⇒ four words ⇒ 2 address bits. Weights are loaded into the 16 PEs once per job and stay resident. A deeper weight memory would be dead silicon.
vio_a_addr8a_mem256 × 32Holds a whole stream of activation vectors. 256 words = up to 256 vectors multiplied against a single weight load without reloading weights.
That asymmetry is the weight-stationary argument, made concrete in the port widths: weight traffic is ROWS × COLS bytes per job, activation traffic is ROWS bytes per vector. You pay the weight-load cost once and amortise it over many activation rows. An 8-bit weight address would be 64× wider than anything the design can use; a 2-bit activation address would cap you at four vectors and throw away the entire economic point of the architecture.

vio_o_addr is likewise 8 bits — output_mem is 256 × 128, mirroring a_mem's depth, because the design produces one result vector per activation vector.
Initial values matter A VIO probe_out comes up at its configured initial value after configuration, and Vivado's dashboard also re-applies stored values when you reopen it. Setting probe_out1 = 0x04 means a freshly programmed board is already configured for a four-vector job — one less thing to get wrong. Leave every command bit (probe_out0/6/9) at 0 so nothing fires at power-up.

Sizing the trace buffer Total probe width = 1+1+1+3+1+1+8+128+128+16 = 288 bits. At depth 1024 that is 288 × 1024 = 294 912 bits ≈ 8 BRAM36 on xc7z020 (140 available), plus a little for the trigger logic. If you are tight on block RAM, or you only care about the job itself, drop Sample Data Depth to 256 — the whole 17-cycle job still fits with room to spare, and the cost falls to ~2 BRAM36. Alternatively drop probe7 (o_rdata), since you can read the same data from the VIO dashboard after the run.

8. Probing internal nets without editing the RTL

The ILA instantiated in vio_debug_top can only see signals visible at the harness level. To watch what happens inside the accelerator — the AGU's wload and valid_in strobes, the address counters, the partial sums crossing the PE array — you need netlist nets. Since the RTL must not be edited, there are two non-invasive routes.

8.1 Route A — the Set Up Debug wizard RECOMMENDED FOR EXPLORING

  1. Run Synthesis once and Open Synthesized Design.
  2. In the Netlist pane, expand vio_debug_top → u_acc. Right-click nets of interest — agu_wload, agu_valid_in, agu_out_we, agu_w_addr[1:0], agu_act_addr[7:0], agu_out_addr[7:0] — and choose Mark Debug.
  3. Tools → Set Up Debug → Next → review the net list → Next → confirm the debug clock domain is clk for every net → set sample depth 1024 → Next → Finish.
  4. Vivado writes create_debug_core / connect_debug_port commands into your XDC. Save it. This inserts a second ILA (u_ila_0) alongside your instantiated ila_0; both appear in the Hardware Manager as separate dashboards.
  5. Re-run Synthesis → Implementation → Generate Bitstream.

8.2 Route B — MARK_DEBUG from the XDC RECOMMENDED FOR REPEATABILITY

The wizard's output is verbose and tied to one particular netlist. For a setup you want to reproduce, put the marking in your own constraints file instead. vio_debug.xdc ships with these lines commented out:

set_property MARK_DEBUG true [get_nets u_acc/agu_wload]
set_property MARK_DEBUG true [get_nets u_acc/agu_valid_in]
set_property MARK_DEBUG true [get_nets u_acc/agu_out_we]
set_property MARK_DEBUG true [get_nets {u_acc/agu_w_addr[*]}]
set_property MARK_DEBUG true [get_nets {u_acc/agu_act_addr[*]}]
set_property MARK_DEBUG true [get_nets {u_acc/agu_out_addr[*]}]
Find the real net names first — do not guess Synthesis renames, merges and absorbs nets. Before uncommenting anything, open the Synthesized Design and run these in the Tcl console: 
get_nets -hierarchical *agu_wload*
get_nets -hierarchical *agu_valid_in*
get_nets -hierarchical *agu_out_we*
Paste back whatever they actually return. An empty result means the net was optimized into its consumer — see the next box.
Preserve hierarchy so the names survive Settings → Synthesis → -flatten_hierarchy → set to none. The default (rebuilt) flattens for optimization and then reconstructs names, which is usually good enough but occasionally loses a net. Setting none guarantees the hierarchical names above resolve. It does cost some QoR — with a measured baseline of WNS +1.279 ns (§15) there is room for that, but check timing after changing it rather than assuming. If a specific net still disappears, add set_property KEEP true [get_nets …] or set_property DONT_TOUCH true [get_cells u_acc/u_agu].

8A. How the VIO and ILA get wired in, and how the build is staged

Sections 6 and 7 told you which boxes to tick in the IP wizards, and section 4 showed vio_debug_top.sv instantiating vio_0 and ila_0 by name. What neither explained is the part that confuses almost everyone the first time: you never instantiate the debug hub, you never write a single line of JTAG logic, and you never connect the cores to the outside world — yet the Hardware Manager finds them. This section explains exactly what Vivado does on your behalf, at which stage of the build it does it, and how to verify each step.

8A.1 There are two completely different ways a debug core enters a design

Both end up in the same place. Confusing them is the source of most "why is my ILA not there" questions.

8A.2 Path A in detail — what "generating the IP" actually produces

When you click OK in the VIO wizard, Vivado writes an .xci file — the IP configuration. Generate Output Products then turns that configuration into real files:

ArtefactWhat it is and who consumes it
vio_0.xciThe IP definition — every parameter you set (probe counts, widths, initial values). This is the file to keep in version control; everything else is regenerable.
vio_0_stub.vAn empty module with the right port list. Lets the top level elaborate and synthesize while the real contents are compiled separately.
vio_0.veo / .vhoA copy-paste instantiation template. This is where the exact port names in section 4's instantiation came from.
vio_0.dcpThe synthesized checkpoint. By default IP is synthesized Out-Of-Context (OOC) — as its own little run, before and independently of your top-level synthesis.

The binding is by module name, and that is the whole trick. Your HDL says vio_0 u_vio (...); the IP produced a module called vio_0; the elaborator matches them. If you rename the IP component in the wizard to anything other than vio_0, the instantiation in vio_debug_top.sv becomes a black box and the design will synthesize with an "unresolved module" warning and then behave as if the VIO were not there.

The single most common Path A failure The component names in the wizard must be exactly vio_0 and ila_0, because that is what vio_debug_top.sv instantiates. If the Sources tree shows those instances with a black-box icon, or synthesis warns about an unresolved black box, the IP was never generated or was generated under a different name. Do not proceed to implementation — the build will complete and the dashboards will simply be absent.

8A.3 What is genuinely automatic — the debug hub

Search vio_debug_top.sv for a JTAG port, a TAP controller, or anything named dbg_hub. There is nothing. The module has one port: clk. And yet the Hardware Manager talks to both cores over the programming cable. Here is the missing piece:

MechanismWhat happens, and why you never see it in your source
The hub interface on each core Every Xilinx debug core carries a dedicated hub-side interface (the sl_iport / sl_oport ports) in addition to the probe* ports you connected. The IP wizard does not show it and the instantiation template omits it, because you are not meant to connect it — the tool does.
Hub insertion During opt_design, Vivado scans the netlist for debug cores whose hub interface is unconnected. The JTAG connection The hub instantiates a BSCANE2 primitive — the fabric's tap into the device's boundary-scan chain — on user scan chain 1 by default (C_USER_SCAN_CHAIN). No package pins are consumed: the JTAG pins are dedicated configuration pins that exist whether you use them or not. This is precisely why a VIO/ILA design needs only one user pin.

One hub, one scan chain A design has exactly one dbg_hub serving all debug cores, however many you instantiate. If you ever add a JTAG-to-AXI master or a second debug infrastructure, they must sit on different user scan chains (C_USER_SCAN_CHAIN 1 vs 2 vs 3), or they will fight over the same BSCAN resource and neither will enumerate.

9.1 The constraints file

vio_debug.xdc is short because there is exactly one physical pin:

set_property -dict {PACKAGE_PIN Y9 IOSTANDARD LVCMOS33} [get_ports clk]

    set_property C_CLK_INPUT_FREQ_HZ   100000000 [get_debug_cores dbg_hub]
    set_property C_ENABLE_CLK_DIVIDER  false     [get_debug_cores dbg_hub]
    set_property C_USER_SCAN_CHAIN     1         [get_debug_cores dbg_hub]

Verify the clock pin against the Digilent master XDC Y9 is the 100 MHz PL oscillator on the widely used ZedBoard rev C/D master constraints. Board revisions differ. Download the official zedboard_master.xdc for your revision and confirm the PACKAGE_PIN and IOSTANDARD before you build. A wrong clock pin produces a bitstream that programs successfully and then does absolutely nothing — the hardest kind of failure to diagnose.
The debug-hub clock block is the single most valuable constraint here Vivado auto-inserts a dbg_hub to bridge JTAG to your VIO and ILA. If it does not know the clock frequency it guesses, and the Hardware Manager then reports "The debug hub core was not detected" — you get a programmed device with no dashboards at all. Setting C_CLK_INPUT_FREQ_HZ to the real 100 MHz and disabling the clock divider fixes the overwhelming majority of these cases.

9.2 Build

  1. Run Synthesis (Flow Navigator → Run Synthesis → OK). Expect zero errors. Warnings about the unconnected btnl/btnr-style ports do not apply here — vio_debug_top has one port.
  2. Run Implementation → OK.
  3. Check timing. Reports → Timing → Report Timing Summary. WNS must be positive. For reference, the accelerator alone synthesizes to WNS +1.279 ns at 100 MHz (§15) — a working margin, but not a huge one, and the debug cores you are adding will eat into it. Check your create_clock first because that is cheap to verify, but treat a negative WNS as a real result rather than assuming it must be a constraint typo.
  4. Generate Bitstream → OK.
If timing fails You have an easy escape here that most designs do not: none of the four interface methods depends on throughput. Add an MMCM and clock the fabric at 50 MHz, which doubles the available period and makes the problem disappear. Remember to update C_CLK_INPUT_FREQ_HZ on the debug hub to match, or you will trade a timing failure for a "debug hub not detected". Reducing the ILA sample depth also helps, since it frees both block RAM and the routing around it.

11.7 result_flat reads all zeros — this is correct, not a fault

Do not read results from result_flat on the VIO dashboard. It will always be 0. This is the single most common confusion with this harness, and it is a property of the architecture, not a bug in the design, the harness or the probe.

There are two different result paths, and only one of them is observable from VIO:

ProbeWhat it isValid whenReadable from VIO?
o_rdata
probe_in3		 Stored result — a registered read port on output_mem Persistently, any time after the job, for as long as you leave the memory alone YES — this is where you read results. Set vio_o_addr, read o_rdata.
result_flat
probe_in4		 Live combinational bus straight off the de-skew buffer, ahead of the output SRAM For four clocks total — samples 13–16 of a 17-clock job NO. Use the ILA (probe8).

Why it is exactly zero rather than stale garbage

Walk the timeline. The four result vectors cross result_flat during DRAIN and are captured into output_mem by the AGU's write strobes. After the last one, the array keeps draining: valid_in is 0, so each PE takes the pass-through path (psum_q <= psum_in) rather than accumulating, and the north edge is driven with zeros because wload_q is 0. Those zeros march south one row per clock, clearing the weight residue out of the psum_q registers as the first activations enter behind them. Within a few cycles of DONE the entire fabric — and therefore result_flat — has settled to 0, and it stays there until the next job.

Now compare the timescales:

window in which result_flat carries data :   4 clocks   =    40 ns
whole job                               :  17 clocks   =   170 ns
one JTAG round trip to refresh the VIO  :             ~   1-10 ms

                       ratio  ~ 1 : 100 000+

VIO samples when you click refresh. The probability of that landing inside a 40 ns window is effectively zero, and even if it did, VIO has no trigger — it cannot wait for the interesting moment. So the dashboard shows the settled value, which is 0. A VIO probe on a live datapath bus is the wrong instrument. That is precisely the division of labour between the two cores: VIO is for state you can take your time over, the ILA is for events.

So why is result_flat wired to the VIO at all? Honestly, mostly for symmetry with the ILA probe list and as a sanity anchor — an all-zero reading confirms the fabric drained cleanly, which is a real (if weak) health signal. If you find it more confusing than useful, delete probe_in4 from the VIO instantiation and drop Input Probe Count from 6 to 5. Nothing else in this document depends on it. Keep it on the ILA (probe8) — there it is one of the most valuable signals you have, because that is where you watch C0…C3 emerge one per clock (§13.3).
The same reasoning applies to phase and busy phase will read 0 (IDLE) and busy will read 0 every single time you look, for the same reason — the job is over 170 ns after you launch it. They are on the VIO so you can confirm the accelerator is idle and ready before loading, not so you can watch a job progress. To watch a job progress you need the ILA. The probes that are meaningful on the VIO after a run are done_sticky and done_count, and they are meaningful precisely because the harness added hardware to latch transient events into persistent state.

13. Reading the ILA waveform — the expected cycle map

This is what Method 2 exists for. The design has fixed, derivable latency and no back-pressure anywhere, so every number below is a hard constant you can check the silicon against.

  2. In Trigger Setup, click + and add probe0 (start_p).

13.2 The cycle map for a four-vector job

Let sample 0 be the sample in which start_p is high. With num_vectors = 4:

SamplephasebusyCyclesWhat is happening
00 IDLE01start_p = 1. The FSM samples it (it is only sampled in IDLE).
1 – 41 WLOAD14 = ROWSWeight rows shifted into the array's north edge, bottom-first: the AGU drives w_addr = 3, 2, 1, 0 with wload = 1.
5 – 82 COMPUTE14 = num_vectorsOne dense activation vector per clock, valid_in = 1. act_addr walks act_base+0…3. COMPUTE follows WLOAD directly — there is no FLUSH phase.
9 – 163 DRAIN18 = STORE_LATENCYThe last vector is still in flight through the array and the de-skew pipe. The four result writes land at samples 13–16; the weight residue left by WLOAD clears the result bus at sample 12.
174 DONE01done pulses for exactly one clock. Note busy is already low.
18 →0 IDLE0—done_count has incremented by 1; done_sticky is set.
Weight reuse: if no host_w_we has occurred since the previous job, WLOAD is skipped entirely — samples 1–4 are COMPUTE, DRAIN runs 5–12, DONE at 13. The ILA is the easiest place to see this: the phase probe goes 0 → 2 with no 1 in between.

Total = 4 + 4 + 8 + 1 = 17 = num_vectors + 13 (13 clocks when the weight load is skipped). Counting the phase-enable widths on the waveform and getting 4 / N / 8 / 1 is the strongest single confirmation that the hardware matches the specification.

13.3 Result checkpoints

Two derived latencies govern when data appears. Both are measured from the cycle in which the activation address is issued:

ConstantValueDerivationObservable as
L1 result latency6ROWS+COLS−2  (3 down a column, +c east, +(COLS−1−c) de-skew — the c terms cancel)Independent of column: all four lanes align on the same clock.
L2 result latency71 (a_mem read) + 6result_flat (probe8) shows Ci around sample 18+i → samples 18, 19, 20, 21.
STORE_LATENCY8result latency + 1 (strobe one cycle after data is observable)out_we fires around samples 19, 20, 21, 22 — all four inside DRAIN, which is exactly why DRAIN is 8 cycles long.

On result_flat (probe8) you should see, one per clock:

C0 = 0000_0004 0000_0003 0000_0002 0000_0001   ->  [  1  2  3  4 ]
C1 = 0000_0008 0000_0007 0000_0006 0000_0005   ->  [  5  6  7  8 ]
C2 = 0000_000C 0000_000B 0000_000A 0000_0009   ->  [  9 10 11 12 ]
C3 = 0000_0028 0000_0024 0000_0020 0000_001C   ->  [ 28 32 36 40 ]
Allow ±1 sample when matching these against the ILA The design documentation distinguishes carefully between a value issued at cycle n (the value the n-th edge samples) and observed at cycle n (the value just after that edge). Conflating the two caused two of the three historical defects found during verification. The ILA registers its probes, so a given sample index may sit one clock either side of the "issued" convention used in the table. Phase lengths (4/6/N/8/1) are exact and unambiguous — anchor on those. Treat the result-checkpoint sample numbers as ±1 and check the spacing (one clock apart, four in a row) rather than the absolute index.

13.4 What a healthy capture looks like

  • start_p — a single 1-clock spike, never a plateau.
  • busy — high for exactly 22 samples, then low before done fires.
  • phase — the staircase 0→1→2→3→4→5→0 with widths 1/4/6/4/8/1.
  • done — one 1-clock spike at sample 17 (13 if WLOAD was skipped).
  • done_count — increments by exactly 1 within the window.
  • result_flat — quiet until the first result lands, then four distinct values on four consecutive clocks late in the run.
  • w_we_p / a_we_p — if the trigger window reaches back far enough, single 1-clock spikes only. Any plateau means a one-shot was optimized away.

14.1 Multi-condition triggers

Change Trigger Mode from BASIC_ONLY to BASIC_OR_TRIG_IN or use the Advanced Trigger state machine for sequences. A useful one here: "trigger when phase enters DRAIN and result_flat is still zero" catches a de-skew-depth bug, one of the failure modes the design's own coverage notes flag as capable of going silently wrong.

14.2 Trigger position

The Trigger position in window field decides how the 1024 samples are split between pre- and post-trigger. Since the whole job is 17 samples, almost any position works; the value only matters when you want to see what happened before the trigger.

14.3 Capture control (storage qualification)

If you enabled Capture Control when generating the ILA, you can set a storage condition such as busy == 1, so the buffer only stores samples during jobs. With a 17-cycle job and a 1024-sample buffer, this lets one capture hold ~44 consecutive jobs back to back — the fastest way to spot an intermittent failure across a sweep.

18. Writing an XDC for any design — a general guide

Everything up to here has been specific to this accelerator. This section is not: it is a self-contained guide to writing Xilinx Design Constraints for any architecture on any 7-series or UltraScale part. The accelerator's own vio_debug.xdc is a deliberately tiny example — one pin, one clock — so it teaches almost nothing about the general problem. Most designs need far more.

The mental model that makes XDC make sense An XDC file is not a configuration file. It is a Tcl script that Vivado executes top to bottom against an in-memory netlist. Three consequences follow, and nearly every beginner XDC bug traces to forgetting one of them:
  1. Order matters. Later commands overwrite earlier ones. Two create_clocks on the same port means the second wins silently.
  2. Objects must exist when the line runs. get_ports can only find a port that survived synthesis. If it was optimized away, get_ports returns empty and the set_property silently does nothing.
  3. An empty get_* is not an error by default. This is the single biggest trap — see §18.8.

18.1 The five jobs an XDC does

#JobCommandsRequired?
1Define clockscreate_clock, create_generated_clockAlways. Without this, nothing is timed and every path reports as unconstrained.
2Place and configure I/OPACKAGE_PIN, IOSTANDARD, DRIVE, SLEW, PULLUPAlways, for every top-level port that reaches a pin.
3Constrain I/O timingset_input_delay, set_output_delayWhenever an interface must meet timing against something off-chip.
4Declare timing exceptionsset_false_path, set_multicycle_path, set_max_delay, set_clock_groupsWhenever the default single-cycle assumption is wrong — CDC, resets, quasi-static config.
5Set bitstream / config propertiesBITSTREAM.*, CONFIG_VOLTAGE, CFGBVSOften required for the bitstream to generate or the device to boot.

18.2 Clocks — get this right first

Every other timing constraint is meaningless without a clock definition. Constrain the source, not the net.

# --- a primary clock arriving on a package pin ---
create_clock -name sys_clk -period 10.000 [get_ports clk]          ;# 100 MHz, 50% duty

# --- explicit duty cycle / phase if not 50% ---
create_clock -name odd_clk -period 8.000 -waveform {0.000 3.000} [get_ports clk2]

# --- a differential pair: constrain the P side only ---
create_clock -name ref_clk -period 5.000 [get_ports clk_p]

# --- clocks OUT of an MMCM/PLL: do NOT hand-write these ---
#     Vivado derives them automatically from the primary clock.
#     Only use create_generated_clock for dividers you built in fabric:
create_generated_clock -name clk_div2 -source [get_pins reg/C] -divide_by 2 [get_pins div_reg/Q]
Three clock mistakes that cost days
  • Hand-writing generated clocks for MMCM/PLL outputs. Vivado already creates them. Adding your own produces two overlapping definitions and nonsensical timing. Run report_clocks and look before you write.
  • Constraining a clock net instead of the source port/pin. Use [get_ports clk] or [get_pins …/O], not the buffer output net.
  • Forgetting a clock entirely. Unconstrained paths are simply not analysed. Timing then "passes" while being completely unverified — the most dangerous possible outcome. Always run check_timing.

18.3 I/O placement and standards

# preferred: one -dict per port, both properties together
set_property -dict {PACKAGE_PIN Y9  IOSTANDARD LVCMOS33} [get_ports clk]

# buses need per-bit constraints; note the braces around the index
set_property -dict {PACKAGE_PIN T22 IOSTANDARD LVCMOS33} [get_ports {led[0]}]
set_property -dict {PACKAGE_PIN T21 IOSTANDARD LVCMOS33} [get_ports {led[1]}]

# drive strength and slew (outputs only) - reduce both to cut ground bounce
set_property DRIVE 8    [get_ports {led[*]}]
set_property SLEW  SLOW [get_ports {led[*]}]

# internal pull-up/down for a floating input
set_property PULLUP true [get_ports btn_n]
IOSTANDARD is not cosmetic — it is bank-wide and it is physical Every I/O bank has one VCCO supply, fixed by the board. Every pin in that bank must use an IOSTANDARD compatible with it. Assigning LVCMOS33 to a pin in a 1.8 V bank is a DRC error at best and, if forced through, can damage hardware. This is why you take pin assignments from the board vendor's master XDC rather than inventing them. Note in this project's own files that the ZedBoard's LEDs are LVCMOS33 while its switches and buttons are LVCMOS25 — different banks, different supplies.

18.4 Where pin names actually come from

  1. The board vendor's master XDC. Digilent, Avnet, Xilinx and others publish one per board, with every pin listed and commented out. Download it, uncomment what you need, rename the ports to match your top module. This is the correct workflow — never transcribe pin numbers from a PDF by hand.
  2. Board files. If installed, selecting the board in the New Project wizard lets IP Integrator auto-assign board interfaces.
  3. The package file (<part>_pkg.txt) for raw pin/bank/supply data.
Check the board revision Pinouts change between board revisions. The ZedBoard is a good example — this project's own XDC carries an explicit warning to verify PACKAGE_PIN and IOSTANDARD against the master XDC for your revision. A wrong clock pin produces a bitstream that programs successfully and then does nothing at all, which is the hardest class of failure to diagnose.

18.5 I/O timing — the part most designs get wrong

Placing a pin says where a signal goes, not when it is valid. For any interface that must meet timing against an external device, you must model the outside world.

# SYSTEM-SYNCHRONOUS INPUT: external device and FPGA share a clock.
# Numbers come from the OTHER device's datasheet plus board trace delay.
set_input_delay  -clock sys_clk -max 4.0 [get_ports {data_in[*]}]
set_input_delay  -clock sys_clk -min 1.0 [get_ports {data_in[*]}]

# OUTPUT: -max is the downstream device's setup requirement + trace delay,
#         -min is negative of its hold requirement.
set_output_delay -clock sys_clk -max 3.0 [get_ports {data_out[*]}]
set_output_delay -clock sys_clk -min -1.0 [get_ports {data_out[*]}]

# SOURCE-SYNCHRONOUS: the clock travels WITH the data. Create a virtual
# clock for the external domain and reference that instead.
create_clock -name virt_src_clk -period 10.000
set_input_delay -clock virt_src_clk -max 2.0 [get_ports {src_data[*]}]

# Genuinely asynchronous or quasi-static pins (a DIP switch, a reset button)
# have no meaningful timing relationship - say so explicitly:
set_false_path -from [get_ports {sw[*]}]
set_false_path -from [get_ports rst_btn]
Why this project's XDC has none of these vio_debug_top has exactly one port — the clock. There is no data I/O to constrain, which is why vio_debug.xdc is three lines long. fpga_top (Method 1) does have switches, buttons and LEDs, but they are human-speed and asynchronous, so the correct constraint for them is set_false_path, not an input/output delay. Do not take the brevity of these files as a model for a real interface. A DDR, Ethernet or ADC interface needs every one of the constraints above, taken from the peer device's datasheet.

18.6 Timing exceptions — and the discipline to use them sparingly

CommandUse whenDanger
set_clock_groups -asynchronousTwo clock domains have no phase relationshipThe right tool for CDC. Cleaner and safer than scattering set_false_path. Does not remove the need for real synchronizers.
set_false_pathA path is logically impossible or genuinely doesn't matterTurns timing analysis off for that path. Over-use is how designs "pass" timing and then fail in hardware.
set_multicycle_pathLogic is genuinely given N clocks to settleMust constrain both setup and hold — -setup N then -hold N-1. Doing only setup is a classic silent hold violation.

# the standard, safe CDC pattern
set_clock_groups -asynchronous \
    -group [get_clocks clk_100] \
    -group [get_clocks clk_50]

# a 2-cycle path, done properly - BOTH lines or you have a hold bug
set_multicycle_path 2 -setup -from [get_cells slow/*] -to [get_cells dest/*]
set_multicycle_path 1 -hold  -from [get_cells slow/*] -to [get_cells dest/*]

# bounded async crossing (better than a false path for data)
set_max_delay 5.0 -datapath_only -from [get_cells src_reg] -to [get_cells dst_reg]
An exception is a promise you are making to the tool Every exception tells Vivado "do not check this". If the promise is wrong, the tool cannot catch the bug and you will find it as intermittent hardware misbehaviour that no simulation reproduces. Write the reason in a comment beside every exception. If you cannot state the reason, you do not yet know whether the exception is safe.

18.8 The empty-object trap — the most important thing in this section

A constraint on an object that does not exist does nothing, and by default does not fail 
set_property PACKAGE_PIN Y9 [get_ports clck]     ;# typo: "clck"
get_ports returns an empty list, set_property applies to nothing, you get a warning buried in a log of hundreds, and the build completes. The pin is never assigned. Your design is silently wrong.

Defend against it in three ways:

# 1. Promote the warning to an error while developing
set_msg_config -id "Vivado 12-508" -new_severity ERROR   ;# "No objects matched"

# 2. Assert explicitly for critical objects
if {[llength [get_ports -quiet clk]] == 0} { error "PORT clk NOT FOUND - check top module" }

# 3. Never use -quiet to hide a problem. It suppresses the warning too.

Then always run these three after implementation:

CommandWhat it catches
check_timingUnconstrained clocks, missing I/O delays, unclocked registers — run this first, every time
report_clocksEvery clock Vivado believes exists, including ones it derived. Compare against what you intended.
report_cdcUnsafe clock-domain crossings
report_timing_summaryWNS/WHS and, crucially, the count of unconstrained paths

18.9 Organising constraints on a real project

One monolithic XDC becomes unmaintainable. Split by concern, and control the order — remember the file is executed sequentially:

constraints/
├── 01_clocks.xdc        create_clock, create_generated_clock, clock groups
├── 02_pins.xdc          PACKAGE_PIN + IOSTANDARD (from the board master XDC)
├── 03_io_timing.xdc     set_input_delay / set_output_delay
├── 04_exceptions.xdc    false paths, multicycles, max_delay  (MUST come after clocks)
└── 05_bitstream.xdc     CFGBVS, CONFIG_VOLTAGE, BITSTREAM.*

Set PROCESSING_ORDER when a file must run at a specific stage:

set_property PROCESSING_ORDER EARLY [get_files 01_clocks.xdc]
set_property PROCESSING_ORDER LATE  [get_files 04_exceptions.xdc]

Constraints can also be scoped to a module — essential for reusable IP, so an instance's constraints follow it wherever it is instantiated:

set_property SCOPED_TO_REF  my_uart_core [get_files uart_timing.xdc]
set_property SCOPED_TO_CELLS u_uart_inst  [get_files uart_timing.xdc]

18.11 Checklist before you trust a build

✓Check
☐Every clock is defined — report_clocks shows what you expect and nothing extra
☐check_timing reports no unconstrained endpoints and no missing I/O delays
☐Every top-level port has both PACKAGE_PIN and IOSTANDARD
☐Every IOSTANDARD is compatible with its bank's VCCO on the real board
☐Pin assignments came from the vendor master XDC for your board revision
☐No get_* returned empty — search the log for "No objects matched"
☐Every timing exception has a comment stating why it is safe
☐Every set_multicycle_path -setup has a matching -hold
☐Asynchronous domains are handled with set_clock_groups, and real synchronizers exist in the RTL
☐WNS and WHS both positive, with zero unconstrained paths
☐report_cdc shows no unsafe crossings
The one habit worth forming Run check_timing and read the "unconstrained" counts before you look at WNS. A design with WNS +2 ns and 4 000 unconstrained endpoints is in far worse shape than one with WNS +0.1 ns and zero. Slack on paths nobody analysed is not slack — it is ignorance with a positive number attached.

Appendix A — data packing reference

A.1 The three word formats

weight_mem[r]  bits  [31:24] [23:16] [15:8] [7:0]
                     W[r][3] W[r][2] W[r][1] W[r][0]        int8, lane c = COLUMN c

a_mem[i]       bits  [31:24] [23:16] [15:8] [7:0]
                     A[i][3] A[i][2] A[i][1] A[i][0]        int8, lane r = ROW r

output_mem[i]  bits  [127:96] [95:64] [63:32] [31:0]
                     C[i][3]  C[i][2] C[i][1] C[i][0]       int32, lane c = COLUMN c

A.2 Packing an arbitrary matrix by hand

For a signed byte v, the hex nibble pair is v for 0…127 and v+256 for −128…−1.

word = (byte3 << 24) | (byte2 << 16) | (byte1 << 8) | byte0

Worked example using the architecture document's reference matrices:

                            lane order in the word:  [b3][b2][b1][b0]
W = [  2  -1   3   0 ]      row 0 -> 00 03 FF 02  ->  weight_mem[0] = 0x0003FF02
    [  1   4  -2   5 ]      row 1 -> 05 FE 04 01  ->  weight_mem[1] = 0x05FE0401
    [ -3   2   1   1 ]      row 2 -> 01 01 02 FD  ->  weight_mem[2] = 0x010102FD
    [  0   1   2  -4 ]      row 3 -> FC 02 01 00  ->  weight_mem[3] = 0xFC020100

A = [  1   2   3   4 ]      A0    -> 04 03 02 01  ->  a_mem[0]      = 0x04030201
    [  5  -1   0   2 ]      A1    -> 02 00 FF 05  ->  a_mem[1]      = 0x0200FF05
    [ -2   3   1   1 ]      A2    -> 01 01 03 FE  ->  a_mem[2]      = 0x010103FE

expected C = [ -5  17  10  -3 ]   -> o_rdata = FFFF_FFFD 0000_000A 0000_0011 FFFF_FFFB
             [  9  -7  21 -13 ]   -> o_rdata = FFFF_FFF3 0000_0015 FFFF_FFF9 0000_0009
             [ -4  17  -9  12 ]   -> o_rdata = 0000_000C FFFF_FFF7 0000_0011 FFFF_FFFC

Note the sign extension: negative int32 results appear as FFFF_FFxx. The Tcl helper accel_read sign-extends for you.

Appendix B — full source listing of vio_debug_top.sv

`timescale 1ns/1ps
//=====================================================================
// vio_debug_top.sv  --  VIO + ILA debug harness for the 4x4 systolic
//                       accelerator (Method 2, ZedBoard xc7z020clg484-1)
//
// The ONLY external pin is the 100 MHz PL oscillator (Y9).  Every input
// to the accelerator comes from a Vivado VIO core over JTAG, and every
// output goes back to the same VIO dashboard.  An ILA captures the run
// cycle-by-cycle.  accelerator_system_top is instantiated UNMODIFIED.
//=====================================================================
module vio_debug_top (
    input logic clk                       // 100 MHz PL oscillator, pin Y9
);
    //-----------------------------------------------------------------
    // Power-on reset: hold rst_n low for 65536 clocks (~655 us).
    //-----------------------------------------------------------------
    logic [15:0] por = '0;
    logic        rst_n;
    always_ff @(posedge clk)
        if (!(&por)) por <= por + 1'b1;
    assign rst_n = &por;

    //-----------------------------------------------------------------
    // VIO probe_out -> levels driven from the Hardware Manager dashboard
    //-----------------------------------------------------------------
    logic        vio_start_lvl;      // probe_out0
    logic [7:0]  vio_num_vectors;    // probe_out1
    logic [7:0]  vio_act_base;       // probe_out2
    logic [7:0]  vio_out_base;       // probe_out3
    logic [31:0] vio_w_wdata;        // probe_out4
    logic [1:0]  vio_w_addr;         // probe_out5
    logic        vio_w_we_lvl;       // probe_out6
    logic [31:0] vio_a_wdata;        // probe_out7
    logic [7:0]  vio_a_addr;         // probe_out8
    logic        vio_a_we_lvl;       // probe_out9
    logic [7:0]  vio_o_addr;         // probe_out10

    //-----------------------------------------------------------------
    // Level -> single-cycle pulse
    //-----------------------------------------------------------------
    logic start_p, w_we_p, a_we_p;
    oneshot u_os_start (.clk(clk), .rst_n(rst_n), .lvl(vio_start_lvl), .pulse(start_p));
    oneshot u_os_wwe   (.clk(clk), .rst_n(rst_n), .lvl(vio_w_we_lvl),  .pulse(w_we_p));
    oneshot u_os_awe   (.clk(clk), .rst_n(rst_n), .lvl(vio_a_we_lvl),  .pulse(a_we_p));

    //-----------------------------------------------------------------
    // The accelerator (LEVEL 3) -- instantiated unmodified
    //-----------------------------------------------------------------
    logic [127:0]       o_rdata;
    logic [2:0]         phase;
    logic               busy, done;
    logic signed [31:0] result [0:3];

    accelerator_system_top u_acc (
        .clk          (clk),
        .rst_n        (rst_n),
        .start        (start_p),
        .num_vectors  (vio_num_vectors),
        .act_base     (vio_act_base),
        .out_base     (vio_out_base),
        .host_a_we    (a_we_p),
        .host_a_addr  (vio_a_addr),
        .host_a_wdata (vio_a_wdata),
        .host_w_we    (w_we_p),
        .host_w_addr  (vio_w_addr),
        .host_w_wdata (vio_w_wdata),
        .host_o_addr  (vio_o_addr),
        .o_rdata      (o_rdata),
        .phase        (phase),
        .busy         (busy),
        .done         (done),
        .result       (result)
    );

    //-----------------------------------------------------------------
    // Sticky done + completed-job counter
    //-----------------------------------------------------------------
    logic        done_sticky;
    logic [15:0] done_count;
    always_ff @(posedge clk) begin
        if (!rst_n) begin
            done_sticky <= 1'b0;
            done_count  <= '0;
        end else begin
            if      (start_p) done_sticky <= 1'b0;   // arm for the new job
            else if (done)    done_sticky <= 1'b1;   // latch the 10 ns pulse
            if (done) done_count <= done_count + 1'b1;
        end
    end

    // `result` is an unpacked array; flatten it so VIO/ILA can probe it.
    logic [127:0] result_flat;
    assign result_flat = {result[3], result[2], result[1], result[0]};

    //-----------------------------------------------------------------
    // VIO  (generate as "vio_0")
    //-----------------------------------------------------------------
    vio_0 u_vio (
        .clk        (clk),
        .probe_in0  (busy),            // 1
        .probe_in1  (done_sticky),     // 1
        .probe_in2  (phase),           // 3
        .probe_in3  (o_rdata),         // 128
        .probe_in4  (result_flat),     // 128
        .probe_in5  (done_count),      // 16
        .probe_out0 (vio_start_lvl),   // 1
        .probe_out1 (vio_num_vectors), // 8   initial value 0x04
        .probe_out2 (vio_act_base),    // 8
        .probe_out3 (vio_out_base),    // 8
        .probe_out4 (vio_w_wdata),     // 32
        .probe_out5 (vio_w_addr),      // 2
        .probe_out6 (vio_w_we_lvl),    // 1
        .probe_out7 (vio_a_wdata),     // 32
        .probe_out8 (vio_a_addr),      // 8
        .probe_out9 (vio_a_we_lvl),    // 1
        .probe_out10(vio_o_addr)       // 8
    );

    //-----------------------------------------------------------------
    // ILA  (generate as "ila_0"), trigger on probe0 == 1
    //-----------------------------------------------------------------
    ila_0 u_ila (
        .clk    (clk),
        .probe0 (start_p),      // 1   <- trigger on this
        .probe1 (busy),         // 1
        .probe2 (done),         // 1
        .probe3 (phase),        // 3
        .probe4 (w_we_p),       // 1
        .probe5 (a_we_p),       // 1
        .probe6 (vio_a_addr),   // 8
        .probe7 (o_rdata),      // 128
        .probe8 (result_flat),  // 128
        .probe9 (done_count)    // 16
    );
endmodule


//=====================================================================
// oneshot -- convert a VIO probe_out level into a single-clock pulse on
// its rising edge.  Without this, a held-high `start` relaunches the
// 17-cycle job ~4 million times per second and the ILA never settles.
//=====================================================================
module oneshot (
    input  logic clk,
    input  logic rst_n,
    input  logic lvl,
    output logic pulse
);
    logic lvl_q;
    always_ff @(posedge clk) begin
        if (!rst_n) begin
            lvl_q <= 1'b0;
            pulse <= 1'b0;
        end else begin
            lvl_q <= lvl;
            pulse <= lvl & ~lvl_q;
        end
    end
endmodule
