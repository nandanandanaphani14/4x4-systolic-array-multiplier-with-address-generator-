1. Methodology in one page

The project is verified in simulation first and only then moved to hardware, and the hardware run is deliberately made comparable to the simulation run rather than being a new, separate experiment. That is the whole strategy, and everything else follows from it:

┌───────────────────────────────────────────────────────────────────────────────────┐ │ 1. RTL FROZEN 13 SystemVerilog files. Never edited by any method. │ ├───────────────────────────────────────────────────────────────────────────────────┤ │ 2. SIMULATION BASELINE QuestaSim regression: 11/11 testbenches, 3 680 checks, │ │ 0 mismatches. T5 golden case established as the vector │ │ that will be replayed on hardware. │ ├───────────────────────────────────────────────────────────────────────────────────┤ │ 3. HARNESS, NOT SURGERY A wrapper (vio_debug_top) is added AROUND the design. │ │ It drives the same host_* ports the testbench drove. │ ├───────────────────────────────────────────────────────────────────────────────────┤ │ 4. BUILD + STATIC CHECKS synth → utilization → impl → TIMING (WNS/WHS/WPWS) → │ │ DRC → methodology → bitstream. See timing.pdf. │ ├───────────────────────────────────────────────────────────────────────────────────┤ │ 5. INJECT OVER JTAG VIO probe_out drives weights, activations, control. │ │ No board switches, no serial port, no external pins. │ ├───────────────────────────────────────────────────────────────────────────────────┤ │ 6. OBSERVE TWO WAYS VIO probe_in = the ANSWER (did it compute correctly?) │ │ ILA waveform = the PROCESS (did it compute correctly │ │ for the right reason, cycle by cycle?) │ ├───────────────────────────────────────────────────────────────────────────────────┤ │ 7. COMPARE TO GOLDEN Same T5 matrices as simulation → same expected numbers. │ │ Automated by vio_demo.tcl, which prints PASS / MISMATCH. │ └───────────────────────────────────────────────────────────────────────────────────┘

Step 6 is the part that makes this methodology worth writing down. Reading a correct answer out of a VIO proves the design produced the right numbers. It does not prove the design produced them the way the specification says it should — a design could produce 28 32 36 40 by accident, or by a path that will break on the next input. The ILA closes that gap by capturing the actual 17-cycle execution and letting you check it against a cycle map derived from the RTL: weight load at cycles 1–4, one activation per clock in compute, results landing at a fixed 8-cycle store latency. Answer plus process. Neither alone is sufficient.

2. The governing constraint: the RTL is frozen

The 13 design files in …SIMPLE_ACCEL_RTL/ are the verified artefact. They carry a regression result — 11/11 testbenches, 3 680 checks, 0 mismatches — and that result is only meaningful if the thing running on the board is bit-identical to the thing that was simulated. So:

RuleConsequence for the methodology
No edits to the 13 RTL files Every method adds a wrapper. vio_debug_top, fpga_top and accel_axi all instantiate accelerator_system_top unmodified and drive its existing host_* ports.
No (* mark_debug *) attributes in the source Internal nets are marked for the ILA from the XDC instead — set_property MARK_DEBUG true [get_nets …]. Same effect, zero source changes. See §8.
No debug-only ports added to the design Anything the harness needs that the accelerator does not expose is derived outside it: done_sticky and done_count are built in the wrapper from the existing done pulse.
The host protocol is honoured, not worked around Fixed latency, no back-pressure, weight rows in natural order, start only when busy is low. The harness respects the same contract the testbench did.
Why this matters more than it looks If the hardware build differed from the simulated build, then a hardware mismatch would have two possible causes — a real hardware problem, or the edit — and you could not tell them apart. Freezing the RTL means any mismatch on the board is unambiguously a hardware or setup problem. That is what makes the bring-up debuggable.

4. The two impedance mismatches the harness must solve

A VIO dashboard is driven by a human clicking a mouse. The accelerator is a 100 MHz pipeline that finishes a job in 17 clocks = 170 ns. Those two worlds are about six orders of magnitude apart in time, and connecting them naively fails in two specific ways. Understanding these two problems is understanding the harness.

Mismatch 1 — VIO drives LEVELS; the accelerator wants PULSES

A VIO probe_out holds whatever value you set until you set it again — typically milliseconds later. But start, host_w_we and host_a_we are single-cycle strobes. If start were simply tied to a VIO output held high:

1 ms held high ÷ 10 ns per clock = 100 000 clocks of continuous start
→ the FSM relaunches the 17-cycle job roughly 4 000 times per click
→ done_count jumps by thousands, the ILA retriggers forever, nothing is observable

Solution: a oneshot edge detector converts every 0→1 transition on a VIO level into exactly one clock of pulse:

module oneshot (input logic clk, input logic rst_n, input logic lvl, output logic pulse);
    logic lvl_q;
    always_ff @(posedge clk) begin
        if (!rst_n) begin lvl_q <= 1'b0; pulse <= 1'b0; end
        else        begin lvl_q <= lvl;  pulse <= lvl & ~lvl_q; end
    end
endmodule

Three instances exist — u_os_start, u_os_wwe, u_os_awe. Note the operating consequence: every write is a 0→1→0 sequence, not a single set. You must drive the level back to 0 to re-arm the edge detector for the next write. This is why every write helper in the Tcl script ends with a … 0 call.

Mismatch 2 — done is a 10 ns pulse; VIO samples at human rate

done is asserted for exactly one clock in the PH_DONE state. A VIO reads the fabric only when you click Refresh or when Vivado polls — hundreds of milliseconds apart. The probability of a refresh landing on that single 10 ns window is essentially zero. You will never see done on a VIO.

Solution: latch it in the wrapper, and add a counter:

always_ff @(posedge clk) begin
    if (!rst_n) begin done_sticky <= 1'b0; done_count <= '0; end
    else begin
        if      (start_p) done_sticky <= 1'b0;   // arm for the new job
        else if (done)    done_sticky <= 1'b1;   // latch the 10 ns pulse
        if (done) done_count <= done_count + 1'b1;
    end
end
SignalWhat it answersWhy it is designed this way
done_sticky"Has the job I just launched finished?" Set by done, cleared by the next start_p — so it is self-arming. You never have to remember to reset it manually, which removes an entire class of "stale sticky bit" confusion.
done_count"How many jobs have ever completed?" The cheapest possible health probe. If it increments by exactly 1 per start click, the one-shot works and the FSM is healthy. If it jumps by thousands, the one-shot was optimised away or bypassed. If it does not move at all, the job never launched.
The general lesson Whenever you bridge a slow observer to a fast machine, you need two pieces of glue in opposite directions: edge-detect the slow side's levels so the fast side sees events, and latch the fast side's events so the slow side can see them. Every VIO harness you ever build will need both.

6. The VIO core — exact configuration

Generate from the IP catalog as vio_0, VIO (Virtual Input/Output) v3.0, with 6 input probes and 11 output probes, and Enable Input Probe Activity Detectors ticked.

6.1 probe_in — what the dashboard shows you

PortSignalWidthWhat you learn from it
probe_in0busy1Read this before every start. Must be 0 or the start pulse is ignored.
probe_in1done_sticky1Job complete. Auto-cleared by the next start.
probe_in2phase3FSM state: 0 IDLE / 1 WLOAD / 2 COMPUTE / 3 DRAIN / 4 DONE. At human rate you will essentially always see 0.
probe_in3o_rdata128The result readback path. Four int32 lanes = one output row.
probe_in4result_flat128The array's live result bus — the last row that came out of the de-skew buffer, before it was stored.
probe_in5done_count16Health probe. +1 per start click, exactly.

6.2 probe_out — what you drive

PortSignalWidthRole
probe_out0vio_start_lvl1→ oneshot → start. Launch a job.
probe_out1vio_num_vectors8How many activation vectors this job processes. Set initial value 0x04.
probe_out2vio_act_base8Base address in a_mem to stream from.
probe_out3vio_out_base8Base address in output_mem to write to.
probe_out4vio_w_wdata32One packed weight row (4 × int8).
probe_out5vio_w_addr2Weight row index 0–3. 2 bits because weight_mem is only 4 deep.
probe_out6vio_w_we_lvl1→ oneshot → host_w_we. Commit the weight word.
probe_out7vio_a_wdata32One packed activation vector (4 × int8).
probe_out8vio_a_addr8Activation index 0–255. 8 bits because a_mem is 256 deep.
probe_out9vio_a_we_lvl1→ oneshot → host_a_we. Commit the activation word.
probe_out10vio_o_addr8Which output_mem row to present on o_rdata.
The asymmetric address widths are deliberate, and they encode the architecture vio_w_addr is 2 bits and vio_a_addr is 8 bits. That is not an oversight — it is the weight-stationary dataflow made visible in the interface. The weight matrix is loaded once and held stationary in the array (4 rows, hence 2 bits), while activations are a stream of up to 256 vectors reused against that one weight load. Both take 4 writes for this 4×4 demo, but the activation bus is sized for the real workload.

8. Non-invasive internal probing via XDC

To see inside the accelerator — the AGU strobes, the array's partial sums — you need MARK_DEBUG on internal nets. Since the RTL cannot be edited, this is done from the constraint file:

# 1. Synthesize once, open the Synthesized Design, find the REAL net names:
get_nets -hierarchical *agu_wload*
get_nets -hierarchical *agu_valid_in*
get_nets -hierarchical *psum*

# 2. Then mark them from the XDC and re-run synthesis:
set_property MARK_DEBUG true [get_nets u_acc/agu_wload]
set_property MARK_DEBUG true [get_nets u_acc/agu_valid_in]
set_property MARK_DEBUG true [get_nets u_acc/agu_out_we]
set_property MARK_DEBUG true [get_nets {u_acc/agu_w_addr[*]}]
set_property MARK_DEBUG true [get_nets {u_acc/agu_act_addr[*]}]
set_property MARK_DEBUG true [get_nets {u_acc/agu_out_addr[*]}]
NetWhat it proves when you see it
agu_wloadThe weight-load enable — exactly 4 cycles wide.
agu_w_addrCounts DOWN 3, 2, 1, 0. This is the bottom-first weight rule made visible. The host writes rows in natural order; the AGU reverses them.
agu_valid_inOne cycle per activation vector during COMPUTE.
agu_out_we / agu_out_addrFour write strobes arriving 8 cycles (STORE_LATENCY) after each activation address was issued — the latency derivation, confirmed on silicon.
Prerequisite and its cost Hierarchical net names only survive if synthesis is run with -flatten_hierarchy none. That disables cross-boundary optimisation and genuinely costs QoR. With a measured baseline of WNS +0.714 ns on the debug build there is room for it, but re-check timing after changing it rather than assuming — see timing.pdf §15. Use it while debugging; drop it for a final build.

10. Strategy for inputting data

All data enters through the host_* write ports of accelerator_system_top — the same ports the simulation testbench used. There are two memories to fill and one job to launch.

10.1 The write protocol — three steps per word, always in this order

For each word to write: ┌────────────────────────────────────────────────────────────────────────────────┐ │ 1. set vio_?_wdata = the packed 32-bit word (data first) │ │ 2. set vio_?_addr = the destination index (then address) │ │ 3. set vio_?_we_lvl = 1 → oneshot emits ONE clock of host_?_we │ │ set vio_?_we_lvl = 0 → re-arm the edge detector for the next write │ └────────────────────────────────────────────────────────────────────────────────┘ Data and address are LEVELS and are already stable when the strobe fires. The strobe is an EDGE. Order matters; the 1→0 return is mandatory, not cosmetic.

10.2 The four preconditions

PreconditionWhy, and what happens if you ignore it
busy must be 0 Host writes are masked while the accelerator is running, and a start arriving while busy is high is silently ignored. This is the single most common cause of "all results read 0". Read busy before every write and every start.
rst_n must have released The POR is 65 536 clocks ≈ 655 µs. A JTAG round trip is milliseconds, so in practice this is always satisfied — but it is why "busy reads 1 forever" is never a "wait longer" problem.
Weight rows in NATURAL order 0,1,2,3 The design loads weights bottom-first, but that is the AGU's job — it counts w_addr down 3,2,1,0 during WLOAD. Do not pre-reverse them in the host. If you do, rows 0–2 come out wrong while row 3 still looks right (the all-ones activation row produces column sums, which are insensitive to row permutation) — which is exactly why this bug hides.
Every address you intend to read must be written The memories have no reset. Unwritten addresses return X in simulation and undefined data on hardware.

10.3 Launching the job

set vio_num_vectors = N        ;# how many activation vectors  (4 for the T5 demo)
set vio_act_base    = 0        ;# where in a_mem to start reading
set vio_out_base    = 0        ;# where in output_mem to start writing
pulse vio_start_lvl 1 then 0   ;# oneshot → one clock of `start`

The job then runs to completion with no handshaking of any kind: num_vectors + 13 clocks — 17 clocks = 170 ns for N = 4. There is no ready/valid, no back-pressure, and nothing will stall to wait for you. By the time the next JTAG transaction arrives, the job finished long ago. That is precisely why done_sticky exists and why you poll it rather than done.

num_vectors = 0 is safe The FSM guards it: both WLOAD and IDLE exit to (vec_n == 0) ? PH_DRAIN : PH_COMPUTE. Without the guard, COMPUTE would compare against 8'hFF and sit for 256 cycles issuing garbage writes. It is worth knowing this is handled, because a VIO probe left at its default is an easy way to launch a zero-vector job by accident.

11. Data packing — the lane and address rules

Every word is 32 bits carrying four signed int8 lanes, lane 0 in the LOW byte.

MemoryDepth × widthWord contentAddress meaning
weight_mem4 × 32 (LUTRAM) Word r, lane c = W[r][c]Weight matrix row index, 0–3 (2-bit bus).
a_mem256 × 32 (BRAM) Word i, lane r = A[i][r]Activation vector index, 0–255 (8-bit bus).
output_memN × 128 (BRAM) Word i, lane c = C[i][c] as int32Result row index.

11.1 Worked packing — the T5 golden case

A (4×4) W (4×4) C = A × W (expected) [ 1 0 0 0 ] [ 1 2 3 4 ] [ 1 2 3 4 ] ← A row0 selects W row0 [ 0 1 0 0 ] × [ 5 6 7 8 ] = [ 5 6 7 8 ] ← A row1 selects W row1 [ 0 0 1 0 ] [ 9 10 11 12 ] [ 9 10 11 12 ] ← A row2 selects W row2 [ 1 1 1 1 ] [ 13 14 15 16 ] [ 28 32 36 40 ] ← A row3 = column sums weight_mem a_mem addr 0 ← 0x04030201 (W row0 = 1 2 3 4) addr 0 ← 0x00000001 (A row0 = 1 0 0 0) addr 1 ← 0x08070605 (W row1 = 5 6 7 8) addr 1 ← 0x00000100 (A row1 = 0 1 0 0) addr 2 ← 0x0C0B0A09 (W row2 = 9..12) addr 2 ← 0x00010000 (A row2 = 0 0 1 0) addr 3 ← 0x100F0E0D (W row3 = 13..16) addr 3 ← 0x01010101 (A row3 = 1 1 1 1) ▲ ▲ lane0 = LOW byte = 0x01 = W[0][0] lane0 = LOW byte = A[i][0]
Why T5 is the right vector to replay on hardware It is chosen so that every failure mode announces itself distinctly. The identity rows mean rows 0–2 of the result should literally reproduce the weight rows — so a transposed or lane-swapped read is obvious at a glance. The all-ones row 3 produces column sums 28 32 36 40, which are hand-checkable and are the one row insensitive to weight-row ordering. And it is the same vector that section T5 of tb_accelerator_system_top checks in simulation, so a hardware match is a direct simulation-to-silicon equivalence result, not a new claim.

12. Strategy for watching results

There are three independent observation channels, each answering a different question. Using all three is the methodology; using only the first is guesswork.

ChannelQuestion it answersHow it works
VIO probe_in — o_rdata"Is the answer correct?" Set vio_o_addr to a result row; read the 128-bit o_rdata; unpack four int32 lanes. There is 1 clock of SRAM read latency between address and data — irrelevant here, because a JTAG round trip is about six orders of magnitude longer, so no wait is needed.
VIO probe_in — status"Did it run at all, and is it ready?" busy, done_sticky, done_count. done_count incrementing by exactly 1 per start is the health check; busy is the interlock.
ILA waveform"Did it run correctly, cycle by cycle?" Arm on start_p == 1, cause a run, and read the captured 17 cycles against the expected cycle map in §14. This is the only channel that can see done (a 10 ns pulse), the phase transitions, and the diagonal wavefront emerging.

12.1 Unpacking a result word correctly

The 128-bit word is MSB-first, so hex character positions map to lanes in reverse:

o_rdata[127:96] = chars 0..7 = column 3 o_rdata[ 95:64] = chars 8..15 = column 2 o_rdata[ 63:32] = chars 16..23 = column 1 o_rdata[ 31: 0] = chars 24..31 = column 0 ← lane 0 lives at the END of the string Two traps: · Vivado DROPS LEADING ZEROS, so a small result comes back as a short string. You must LEFT-PAD to 32 hex characters before slicing, or every lane shifts. · Each lane is a SIGNED int32. Values ≥ 0x80000000 must be sign-extended (subtract 0x1_0000_0000), or negative results read as ~4 billion.

12.2 The Tcl semantics that catch everyone

CallWhat it really does
set_property OUTPUT_VALUE … Stages the value locally in Vivado's memory only. Nothing has reached the FPGA yet.
commit_hw_vio <probe> Pushes the staged values over JTAG. Forgetting this is the number-one VIO scripting bug — your script "works" and the hardware never sees a thing.
refresh_hw_vio <vio> Pulls current values from the device. Reading INPUT_VALUE without a preceding refresh returns a stale cached snapshot from whenever the last refresh happened.
get_property INPUT_VALUE …Reads the cached snapshot. Only as fresh as your last refresh.
OUTPUT_VALUE_RADIX / INPUT_VALUE_RADIX Set the radix before the value, or a hex string will be interpreted as binary and silently truncated.

13. Scripted operation — vio_demo.tcl dissected

Manual dashboard clicking is fine once. For a repeatable result the run is scripted. The script is structured defensively because Hardware Manager state is easy to get wrong:

ProcedureWhat it does and the failure it prevents
accel_vio Connects and caches the VIO object. Explicitly selects the xc7z020* device rather than relying on one being current — a bare get_hw_vios silently returns nothing if you clicked elsewhere in the GUI, or if arm_dap_0 is the current device. On failure it prints a four-point checklist rather than an opaque error.
accel_probe {name dir} Resolves a probe by name. Vivado names probes after the attached net, but the exact string varies by version — vio_w_wdata in some, a hierarchical vio_debug_top_i/vio_w_wdata in others. So: exact tail match first, substring match as fallback, always filtered by direction so a value call can never land on the wrong probe, and on ambiguity it lists the candidates rather than silently picking one.
accel_probesPrints every probe with direction and width — the first thing to run when a name lookup fails.
accel_set / accel_getSet-radix → set-value → commit, and refresh → read. The two halves of §12.2, encapsulated so they cannot be forgotten.
accel_write_w <addr> <hex>One weight word: wdata → addr → we 1 → we 0.
accel_write_a <addr> <hex>One activation word, same pattern on the 8-bit address bus.
accel_run <nvec> Sets num_vectors/act_base/out_base, records done_count before, pulses start, then polls done_sticky up to 20 times. Times out with a diagnostic naming the two real causes (POR not released, num_vectors = 0) instead of hanging.
accel_read <addr>Sets o_addr, reads o_rdata, strips separators, left-pads to 32 hex chars, slices from the end backwards, and sign-extends each int32. Returns col0-first.
accel_demo The whole regression: load 4 weight words, load 4 activation words, run, read all 4 result rows, compare against the golden matrix, and print PASS or a per-row MISMATCH exp=….

14. The expected ILA cycle map

This is the reference the captured waveform is checked against. Cycle 0 is the clock on which start_p is high; every number is a hard constant derived from the RTL, not an approximation — which is exactly what makes the capture checkable.

CyclephasePhase name LengthWhat you should see on the probes
00 → 1IDLE → WLOAD1start_p high for exactly one clock; busy rises.
1–41WLOADROWS = 4 Weight rows driven into the array's north edge bottom-first: W[3], W[2], W[1], W[0]. If agu_w_addr is marked, it counts down 3,2,1,0.
5–82COMPUTEN = 4 One dense activation vector per clock, valid = 1. A0@5, A1@6, A2@7, A3@8. This is the throughput claim — once the pipe is full it is one vector per clock. COMPUTE follows WLOAD directly: there is no FLUSH phase.
9–163DRAINSTORE_LATENCY = 8 The last vector is still in flight. Results land here: watch result_flat populate and, if marked, four agu_out_we strobes at cycles 13–16. The weight residue left in psum_q by WLOAD leaves the de-skewed result bus on cycle 12, one clock before the first strobe.
174DONE1 done pulses for exactly one clock. busy is already low. done_count increments by 1.
Total job length = ROWS + N + STORE_LATENCY + 1 = 4 + N + 8 + 1 = N + 13
Reusing the loaded weights (WLOAD skipped) = N + STORE_LATENCY + 1 = N + 9
For N = 4: 17 clocks = 170 ns, or 13 clocks = 130 ns reusing weights, at 100 MHz
Two changes from earlier revisions — both visible on the ILA 1. There is no FLUSH phase. The FSM used to insert ROWS + 2 = 6 cycles between WLOAD and COMPUTE to push weight residue out of the psum_q registers. It was margin, not function — the residue clears the de-skewed result bus a full cycle before the first out_we fires — so it was removed, cutting 6 clocks from every job. Phase encodings shifted with it: 0 IDLE, 1 WLOAD, 2 COMPUTE, 3 DRAIN, 4 DONE.

2. WLOAD is skipped when the weights have not changed. accelerator_system_top keeps an internal weights_dirty flag — set by reset and by any host write to weight_mem that reaches the SRAM, cleared on the last WLOAD cycle — and drives controller.load_weights with it. Run the same weights twice and the second job takes 13 clocks instead of 17. This is the easiest thing to confirm on the ILA: arm on start_p, run a job, then run it again without touching the weight probes — on the second capture the phase probe steps 0 → 2 directly, with no 1 in between. Nothing in the host protocol changes and the module's port list is unchanged, so fpga_top, vio_debug_top and accel_axi all benefit untouched.

14.1 The latency chain, and where to see each term

#StepAddsRunning totalVisible as
1Down a PE column (one register per row)ROWS−1 = 33Bottom-row psum appears 3 cycles after the vector enters.
2East to column c+c3+cColumn c's value is ready at n+3+c — the diagonal wavefront.
3De-skew pipe (COLS−1−c)+(3−c)6 — independent of cAll four lanes of result_flat align on the same clock.
4a_mem read latency+17 = RESULT_LATENCYResult valid relative to the address issued.
5Write strobe, one cycle after data is observable+18 = STORE_LATENCYagu_out_we pulses, and DRAIN is exactly this long.
Step 3 is the elegant part, and it is worth pointing at in a review Column c's result is ready at 3+c — a diagonal wavefront, four different arrival times. The de-skew buffer delays column c by 3−c. The two cancel exactly, so the sum is 6 for every column and the whole result row emerges aligned on one clock. Seeing that alignment on the ILA is direct confirmation that the output skew buffer is doing its job.

19. Alternative methods 1, 3 and 4 — when to use them

19.1 Method 1 — switches and LEDs (fpga_top.sv)

A console FSM around the accelerator: enter each int8 byte on SW[7:0], commit with BTNC (the pointer auto-advances), 16 commits for weights then 16 for activations; BTNU runs the job; then SW[5:4] selects the result row and SW[3:0] selects the byte within that row's 128-bit word, and the LEDs display it. BTND resets entry. Use it when you want a self-contained board demo with no PC attached at run time. Sanity check: with T5 loaded, SW[5:4] = 11, SW[3:0] = 0000 → LEDs 00011100 = 28.

19.2 Method 3 — USB-UART text console (accel_axi.sv + accel_monitor.c)

On the ZedBoard the USB-UART is a PS resource (UART1, MIO48/49), so this needs a minimal Zynq PS with accel_axi bridging AXI-Lite to the accelerator. Data path: terminal → USB → PS UART1 → ARM → AXI-Lite → accel_axi → accelerator (PL). Register map (byte address = index × 4): 0 NUMVEC · 1 ACT_BASE · 2 OUT_BASE · 3 W_WDATA · 4 W_COMMIT · 5 A_WDATA · 6 A_COMMIT · 7 START · 8 O_ADDR · 9 STATUS(busy,done,phase) · 10–13 ORD0–3. Note the same architectural pattern as the VIO harness: a commit register that turns a bus write into a one-cycle strobe, and a sticky-done bit — the two mismatches of §4 recur, because they are inherent to bridging a slow host to a fast pipeline. Use it when a human needs to type matrices and read results in text. Terminal: 115200 8-N-1, no flow control.

19.3 Method 4 — full PS/AXI integration

What you add on top of Method 3 for real workloads: AXI-DMA to stream a block of activation vectors into a_mem and read the result block back instead of one word per register write; a done-interrupt routed to IRQ_F2P and enabled in the PS7 GIC so software is event-driven instead of polling the sticky bit; Linux/UIO under PetaLinux with an mmaped register block; and benchmarking with up to 256 activation vectors (the depth of a_mem) — once the pipe is full it is one vector per clock.
